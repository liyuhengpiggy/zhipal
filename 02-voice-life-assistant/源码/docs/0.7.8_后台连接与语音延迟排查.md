# 0.7.8 后台连接与语音延迟排查

“BLE 传得久”需要拆成硬件录音、传输、手机转文字、后续业务四段测量。目前没有手机和硬件实测数据，不能直接归因于软件或固件。本版补了接收进度、速度与分阶段日志，并改进手机收包和后台重连，方便用同一段录音定位。

## 日常不再重复进入原生调试页连接

首次只需打开整合首页“设置”，允许系统蓝牙权限，点击“搜索附近设备”，选择自己的硬件。手机只有成功订阅约定 Notify 通道后才记住设备及 UUID；“系统蓝牙已配对”不能代替 App 内显示“可双向收发”。硬件广播名由固件决定，本项目未证实一个固定名字。

连接后确认“自动重连已记住的设备”已勾选、后台连接正在运行。之后可以回桌面、进入微信等其他 App；硬件重新开机或回到附近时，后台服务尝试连接已记住的设备，不会自行连接陌生设备。手机蓝牙重新开启后也会恢复尝试。每次失败按 1、2、5、10、20、30 秒退避，最长维持 30 秒间隔；系统的等待上线连接本身也需要时间，不承诺开机立即连上。

“断开设备”“停止后台连接”或通知里的“暂停连接”表示用户主动暂停，不应立即自动连回；需要时在设置恢复后台连接。自动重连关闭时仍可手动选择设备。首次设备选择、附近设备权限和可能出现的系统安全配对框，需要用户完成一次，软件不能替系统默许。

后台服务带持续运行通知，并在系统允许时恢复被回收的服务；已开启连接的设备还会在手机重启或覆盖安装后尝试恢复。系统“强行停止”、撤销权限或厂商禁止启动会阻止恢复，需重新打开助手并恢复权限。普通返回桌面不等于强行停止。

华为 Mate30 的一次性准备：进入手机管家或系统设置的“应用启动管理”，找到“语音生活助手”，改为手动管理，允许自启动、关联启动、后台活动；允许持续通知。具体菜单名称以手机为准。软件设置中提供“后台运行设置”入口与说明。后台打开 App、拨号和 B 页面操作还需开启助手无障碍服务，并保持手机解锁。锁屏时后台接收和识别仍需测试，不能据此认为锁屏下能执行全部手机操作。

B 的屏幕观察另需开启无障碍并明确开始本次观察；自动恢复 BLE 不自动恢复截图同意。用户强停后不能承诺继续收语音，这与 App 是否在前台是不同情况。

## 首页现在显示什么

首页显示本次任务的阶段和结果：录音 → 接收 → 转文字 → 处理 → 结果。接收时显示已收/总量、百分比和 KB/s；细化状态包括正在校验录音、准备语音模型、视觉识别、等待语音确认和失败。某些旧固件只在录完后才发消息，手机收不到 `button_start` 前无法显示真实“正在录音”。

速度是接收到的音频有效载荷平均速度，不是无线链路理论速度。JSON/Base64 传输按解码后的音频字节计算；生成的 WAV 头不算 PCM 载荷。首页的 KB/s 按 1024 字节换算。v1 文字帧跳过手机 ASR，所以不会出现一段完整的音频接收进度。

联调明细已放到“设置 → 查看联调日志”，高级接口设置仍可用。记录同步、模型预热和 B 观察状态分别维护，不再让普通同步提示顶掉本次指令结果。网络详细日志不应占首页主要结果区。

## 本版做的手机侧改进

- BLE 通知进入一个有序接收工作线程，避免每个小包都先排队到主线程；裸 WAV 使用缓冲写盘。
- 接收进度按约 250 毫秒更新，半帧超时使用周期检查，减少每个通知反复修改主线程定时器的负担。
- 连接时申请 MTU 247 和高连接优先级，MTU 与通知订阅按序执行；设备页显示实际协商结果。申请值不是保证值，固件仍须按实际能力发送。手机发送 ACK、capture 等命令继续按最多 20 字节分片兼容旧固件；扩大 MTU 用于提高硬件通知的可用接收容量，不代表手机改变了既有下行分片约定。
- 后台服务启动或 BLE 就绪时预热本地 Vosk 模型；后续录音复用模型，不把首次复制/加载的等待都推到收到录音之后。
- 接收和识别期间使用有时限的 CPU 唤醒锁；结果或任务停止时释放。它不等于绕过系统后台管理。

这些改动能减少手机侧开销，实际改善幅度仍需下面的对照测试确认。不能把提高 MTU 等同于固件已改为大包发送。

## 为什么“以前快、现在慢”可能有不同原因

先确认以前传的是 v1 识别文字、完整 WAV，还是同规格 PCM。文字帧通常只有几十到几百字节；16 kHz、单声道、16-bit PCM 每秒 32000 字节，3–5 秒需要 96000–160000 字节。WAV 头通常只多 44 字节，本身不会造成数量级变慢。

JSON/Base64 则约增加三分之一数据量，另有 JSON 字段开销。若现在改成 48 kHz 或双声道，原始数据还会变为原来的 3 倍或 2 倍。以 5 秒、16 kHz 单声道音频为例，假设实测音频净速只有 8 KiB/s，仅传输就约 19.5 秒；这不是 ASR 用了 19.5 秒。

| 现象 | 优先检查 | 责任侧与证据 |
| --- | --- | --- |
| “接收中”数值缓慢增长 | 实际 MTU、固件是否仍固定 20 字节、通知发送间隔/队列阻塞、采样率和声道、Base64/JSON 开销 | 手机 KB/s 与 BLE_RX 耗时；固件发送字节数、包数、发送起止时间 |
| 传到某一点长时间不动 | 缺包、事件/长度不符、错误的逐块 ACK 等待、硬件仍被其他 BLE 工具连接 | 固件等待状态与手机最后阶段；错误/超时日志 |
| 文件已收齐，停在模型准备 | 首次复制中文模型、系统回收后重新加载、模型预热是否完成 | `ASR_MODEL preparing/ready/failed` 耗时，设备页模型状态 |
| 长时间停在转文字 | 音频时长/有效 PCM 参数、手机负载、原录音质量 | `ASR started` 到 `transcribed/low_confidence/failed` 耗时；保存的本次录音质量 |
| 文字很快出现，后续才慢 | OCR/物体/B 模型请求、冷启动、上传或轮询、服务器异常 | 同 task 的 HTTP 状态/终态与服务器真实模型耗时 |

## 用同一段 3–5 秒录音做一次可比较测试

1. 选一句固定指令，例如“打开微信”。用同一固件、同一采样率/声道/位深、相近距离和相同录音时长，分别测试旧版和本版。每次只连接一款 App；保留旧 APK 版本与固件版本，避免把协议变化当软件回退对比。
2. 先等离线模型已就绪，做三次，再单独记录一次冷启动。先测前台，再按返回桌面测后台，最后在其他 App 前台测；不要把冷启动和热模型的结果混在一起。
3. 固件记录：按下 A、录音结束、首个音频包发送、最后一个包发送；采样参数、音频字节数、实际分片大小、通知次数与是否等待回传。无需记录音频内容或密钥。
4. 手机从设置导出 JSONL。每次按 session/task/event 对齐 `BLE_RX audio_received` 的 bytes、elapsed_ms、bytes_per_second；再看 `ASR_MODEL`、`ASR started/transcribed/failed` 和 `A result`。页面接收数值截图便于判断增长是否连续。原始硬件采样与串口时间、手机单调计时分别计算，不直接相减两个设备未经同步的时钟。
5. 视觉或 B 任务还要加服务器请求/模型开始/模型结束/终态时间，以及 task/frame/SHA 关联；单次服务器 `/health` 成功不能替代这些证据。

建议记录表：

| 轮次 / 版本 / 前后台 | 音频参数与字节数 | 实际 MTU / 通知载荷大小 | 硬件录音后等待 | 手机音频接收耗时 / KB/s | 模型准备 / ASR 耗时 | 后续业务耗时 | 实际结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 待实测 | 待填 | 待填 | 待填 | 待填 | 待填 | 待填 | 待填 |

判断依据是差异出现在哪一段：同规格音频在手机接收阶段才慢，就对齐固件发送速率、MTU和手机收包；BLE_RX 完成很快而 ASR 很慢，则查模型与音频；文字已出才慢，则查后续业务。不需要先更换 OCR 模型来排查 BLE。

## ACK 与固件发送必须对齐

当前协议在录音元信息可接收时返回 `ready_for_audio`，JSON 音频开始后返回 `audio_started`，完整收齐进入识别时返回 `audio_received`。`audio_chunk` 没有逐块应用层 ACK；固件若每块都等待一个不存在的 ACK，会卡住或等超时。

固件完成 ready/started 握手后，按 BLE 栈实际发送能力、队列可用状态和订阅状态连续有序发送分片；同一 JSON 必须完整结束才发送下一条，不交错两段录音。按实际 MTU 分片，上限通常为 MTU−3；仅协商到较大 MTU但继续固定 20 字节不会自动提速。不要移除长度/序号校验或吞掉缺包来制造“更快”。

## 后台与自动连接回归

| 操作 | 预期 |
| --- | --- |
| 首次搜索选择并成功订阅，再离开设置 | 记住此设备；服务通知存在；不用再打开原生调试页 |
| 回桌面 / 切入其他 App 后真实按 A 或 B 录音 | 接收数值和 ASR 在后台推进，回到首页看到实际结果；B 仍遵守当前 prompt 与确认 |
| 硬件关机再开机 | 检测断线、清半帧/旧任务，自动尝试原设备；新录音可用 |
| 手机蓝牙关再开 | 关闭时显示等待，打开后恢复尝试；权限仍有效 |
| 手动暂停后台连接 | 停止尝试；硬件开机也不擅自连回；恢复连接后再尝试 |
| 覆盖安装 / 手机重启 | 在系统和华为启动管理允许时恢复此前启用的连接；B 截图观察需重新开始 |
| 系统强行停止后按硬件按钮 | 不声称可收到；用户重新打开助手后才能恢复 |

本表尚未在目标手机上验收。测试后把成功/失败、时间和对应手机/固件日志补入正式联调报告。
