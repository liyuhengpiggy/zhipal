# A 文字帧 v1 接入与联调（0.7.5）

## 这版修改后的路径

ESP32 完成语音识别 → 按现有 text_frame.h v1 协议发 BLE 通知 → 手机持续拼接 → 校验完整帧 → 序号去重 → A 指令处理 → 显示文字和执行结果。

手机不再要求这条 A 路径先收到 WAV，也不再对硬件识别文字运行 Vosk。原有 WAV / JSON 接收仍兼容，B 回答仍走带 source_button、task_id、prompt_id 等元信息的原有录音路径。v1 文字帧没有 A/B 来源和确认上下文，因此只作为 A 输入，不能充当 B 的回答或操作确认。

这项改动不要求修改 Render 后端，也不需要在 APK 中添加模型 API Key。ESP32 自己完成识别所需的服务由固件负责。图片识别、照片上传、B Agent 的配置仍按原有流程办理；支持收到问题文字并不意味着固件已支持后续照片任务协议。

## 严格沿用固件协议

| 偏移 | 字段 | 手机检查方式 |
| --- | --- | --- |
| 0 | 帧头 2 B | A5 5A |
| 2 | 版本 1 B | 01 |
| 3 | 类型 1 B | 01 识别文字；02 状态/错误 |
| 4 | 序号 4 B | 无符号小端，0 到 4294967295 |
| 8 | 正文长度 2 B | 小端，UTF-8 字节数，0 到 1024 |
| 10 | 语言 2 B | 类型 01 必须是 ASCII en；类型 02 必须是 -- |
| 12 | 正文 N B | 严格 UTF-8，不接受无效编码或 NUL |
| 12+N | CRC 2 B | 小端 CRC-16/CCITT-FALSE |
| 14+N | 帧尾 2 B | 0D 0A |

完整长度为 N+16。CRC 从偏移 2 开始，共 N+10 字节，含版本、类型、序号、长度、语言和正文。初值 FFFF、多项式 1021、无反射、无末尾异或。标准串 123456789 的 CRC 为 29B1。

手机不把一次 BLE 通知当作一帧，可处理 20 字节分包、任意切分、一包多帧及 UTF-8 字符被分开的情况。长度、CRC、帧尾、版本、类型或语言错误均不执行；遇到损坏帧重新寻找 A5 5A。重同步期间不把坏帧中的内容转交给 JSON 指令解析器。

类型 02 只显示“硬件状态”并存记录，即使正文是 open QQ 或 call Alice，也不会执行、不会确认 B、不会启动新的 A。类型 01 正文为空时提示重新录音，不执行。

当前语言检查仍严格保持 en / --。UTF-8 传输层支持多字节字符，但要正式使用中文识别，需同时约定固件的语言字段和手机的允许值；本版没有自行增加 zh 或改变帧格式。

## 手机上如何验收

1. 安装项目根目录的 `语音生活助手_0.7.5_调试版.apk`。与此前调试版包名相同；同签名时可覆盖更新，保留原有设置。
2. 保持手机解锁，打开助手。“设备与设置” → “打开原生联调设置” → 搜索并连接原有 ESP32，确认显示“已连接并订阅，可以双向收发”。Service / Notify / Write UUID 沿用实际固件配置，不因本次帧格式改动而改 UUID。
3. 请硬件同学按 A 录音，说 **open QQ**。手机应显示“A 硬件识别：open QQ”，输入处理显示“已收到 A 硬件识别文字（v1/en），跳过手机语音识别”。手机安装了 QQ 且允许启动时，应请求打开 QQ。
4. 使用同一序号再次发送完整帧，或在原生联调设置点击“请求重发最近一条文字结果”。应提示“已忽略重复文字帧”，不会再次请求打开或拨号。
5. 发送类型 02、语言 --、新序号的状态帧，例如 recording failed。应只显示硬件状态。
6. 故意改变正文一个字节且不更新 CRC，手机应报 CRC/帧尾校验失败，不执行。点击重发，让固件发送原本正确的帧；若该序号此前未成功接收，则可正常处理。
7. 一帧只发前半段后断开，再重新连接；半帧不能产生指令。新连接从完整帧头重新发送。

英文支持范围是明确单条 `open NAME`、`launch NAME`、`start NAME`、`call NAME`，可有开头 Please。应用名仍匹配手机实际安装的启动器名称，没有增加英语到中文应用名的翻译。例如 open QQ 可匹配 QQ，open WeChat 不保证能匹配名称为“微信”的应用。

拨号需要预先在助手中保存同名联系人，例如 Alice，并授予电话权限。请先用打开应用验证通信；拨号测试会真的请求系统拨号。带多个动作、问句或否定的英文句子不会作为这些直接指令执行。原有中文 WAV 指令仍兼容。

## 不经过麦克风的固件测试帧

下面的完整帧表示：类型 01、序号 0x01020304（16909060）、语言 en、正文 open QQ。正文 7 字节，完整帧 23 字节；CRC 数值 1985，线上小端为 85 19。

```text
A5 5A 01 01 04 03 02 01 07 00 65 6E 6F 70 65 6E 20 51 51 85 19 0D 0A
```

按当前固件方式分两次通知：

```text
通知 1（20 字节）：A5 5A 01 01 04 03 02 01 07 00 65 6E 6F 70 65 6E 20 51 51 85
通知 2（ 3 字节）：19 0D 0A
```

必须发原始字节，不是把上面的十六进制字符串作为 ASCII 发出。仅通知 1 到达时，手机不会执行；通知 2 到达且验证通过后才处理。这个样例也用于独立固定向量测试。

“请求重发”通过现有 Write 通道排队发送精确 ASCII `RESEND\n`（52 45 53 45 4E 44 0A），没有新增重发 JSON，也没有自动重发循环。提示“已排队”不代表固件已收到，结果以随后的通知或写入失败提示为准。原有 A 执行结果仍沿用已有 JSON v2 回传，本次未擅自增加二进制下行结果帧；仅支持 RESEND 的固件可忽略已有 JSON 回传，若需语音播报执行结果应另行确认下行协议。

## A 优先与去重的边界

有效、非空、未重复的类型 01 文字会进入现有 beginA：取消旧 B 的观察、弹窗、录音识别、Agent 请求和候选，随后执行 A；旧 B 的异步回调由原有任务代际检查拦截。类型 02 和重复序号不启动 A。

仅有这套最终文字帧时，手机不知道 A 何时开始录音，因而无法在物理按下 A 的瞬间暂停 B；暂停发生在完整有效文字到达时。如果要求按下 A 就立即抢占，固件还需发送项目现有的 A button_start 元信息事件，并在其后顺序发送结果，不能交错两个消息的字节。

序号在同一次 BLE 连接中去重，包含文字帧和状态帧；不同的新结果应使用不同序号，重发必须保留原序号。坏帧不会占用已处理序号。接收中断 30 秒只清理半帧，不清空当前连接的已处理序号。

断线会丢弃半帧、取消旧任务并清理去重集合；重新连接是新会话。因此不要用“断开重连后重发旧拨号结果”测试防重复。v1 没有硬件启动会话标识，无法区分“重连后的旧结果”和“重启后同序号的新结果”。如果后续需要跨连接、跨进程的执行去重，应与固件共同扩展会话标识，不能只在手机端猜测。

## 实现位置与验证

- `app/src/main/java/cn/seniorvoice/demo/BleTextFrame.kt`：严格文字帧解析、CRC、连接内序号去重和文字/状态分流。
- `app/src/main/java/cn/seniorvoice/demo/BleIncomingStream.kt`：文字 / WAV / JSON 字节流分流，断线/超时半帧清理。
- `app/src/main/java/cn/seniorvoice/demo/BleClient.kt`：后台解析结果通过连接代际检查后回到主线程，断线后的旧回调不执行。
- `app/src/main/java/cn/seniorvoice/demo/assist/AssistRuntime.kt`：A 指令入口、A 优先清理、状态显示和 RESEND 请求。
- `app/src/test/java/cn/seniorvoice/demo/BleTextFrameTest.kt`：固定协议向量、CRC、切包、无符号序号、损坏恢复、严格解码、去重、半帧、A/B 分流及原有 WAV / JSON 兼容测试。
