# 药盒 OCR 接入评估

评估日期：2026-10-23。依据用户提供的 `medicine-vision-apk-integration.zip` 内接口、Python 服务、Kotlin 示例和当前 0.7.0 Android 源码。本次检查未修改 APK、安装 Python 依赖或部署服务。

## 结论与功能归属

可作为 A 按钮的文字与药盒字段识别服务。模型运行在电脑或服务器，手机通过 HTTP API 调用。包内 Python、Paddle 权重不是可直接嵌入 Android 的离线 SDK。

| 使用情景 | 接入安排 |
| --- | --- |
| A：读眼前文字、查药品名称、生产日期、有效期、批号、厂家、用法用量 | 调用新 OCR 任务接口，显示回答和识别原文 |
| A：打开应用、拨打联系人 | 沿用现有本机语音指令流程 |
| A：“这是什么东西”等开放式问题 | 此包无物体识别或生成式问答能力；原视觉服务能力另行验证，不能用 OCR 冒充 |
| B：手机页面停留、判断是否需要帮助 | 保留现有页面视觉服务；此包无法提供页面语义判断和手机操作 agent |

“用法用量”是读取包装上可见的明确文字，不提供针对个人的用药方案。字段候选须保留服务的核对提示；找不到时提示补拍，冲突时展示候选，不自动取一个值。

## 推荐链路：手机建任务，眼镜直接上传本次照片

1. 用户按 A 说“这个药的生产日期是什么”；手机开始 A 任务并清理 B。
2. 手机生成独立服务任务编号，例如 `v_` 加无短横线 UUID，保存它与当前 A 任务、问题、运行世代的映射，POST `/api/v1/vision/tasks`，提交 question 和 `expected_frames:1`。
3. 创建成功后，手机通过 BLE 发拍照请求，附当前 A 任务编号、新服务任务编号、`frame_id:f0`。具体新增字段要与固件一起约定。
4. ESP32 通过 Wi-Fi 向配置服务 PUT `/api/v1/vision/tasks/{服务任务编号}/frames/f0`，Content-Type 为 `image/jpeg`，body 是本次完整 JPEG。地址和凭证须预先配置，不能假定现有固件已支持。
5. 手机约每秒 GET 同一任务；显示“正在识别”，给出明确总等待时间。该服务建议客户端约 240 秒预算，需替换目前 A 图像阶段约 65 秒的限制。
6. 到 `succeeded` 后解析 answer、evidence_text、result.answer_type；失败或超时解析 message/error_code。手机显示、写入本机记录并向硬件返回结果。手机与硬件是否朗读需另接语音输出，包内没有 TTS。

这一方式不要求服务另外提供 JPEG 下载地址，也不读取 `/camera/latest`。手机必须先确认服务建任务成功，板端再上传；不能只凭拍照成功或 HTTP 202 判定识别完成。首次可先做单图，之后再扩展服务支持的 1–4 张同物品不同面。

备用方式是手机取得本次 JPEG 后自行 PUT；但目前 APK 只支持从任务专属 URL 下载照片，尚无 BLE JPEG 接收，因此采用备用方式仍需实现图片传输或提供稳定下载资源。

## APK 必要改动

| 位置 | 改动 |
| --- | --- |
| `assist/AssistSettingsActivity.kt`、运行时设置 | 单独增加 OCR 服务地址和令牌；B 继续使用现有 Render 地址。独立地址便于先在局域网联调，正式可由同一网关转发 |
| 新 OCR API 客户端 | 建任务、查询健康、可选传图、轮询、解析结果、断线后按原编号查询；限制请求和响应大小 |
| `assist/AssistRuntime.kt` | A 识别出支持的文字/药盒问题后进入 OCR 分支；建任务后发新的 capture 元信息；延长等待并保留 A 优先 |
| 结果显示与本机历史 | 同时保存 answer、evidence_text、answer_type 和服务任务编号；处理补拍、候选冲突、不支持、失败 |
| 协议与测试 | 增加服务任务/帧编号、上传结果上报；检查错图、旧任务、切换新 A、断线和迟到结果 |

当前 `VisionClient` 调用 `/vision/analyze` 或 `/analyze`，使用 multipart；新服务使用创建/PUT/GET 异步任务协议，不能只改 URL。当前 `image_ready` 要求照片下载 URL，也不能直接把新服务任务 JSON 填进去。

现有固件任务编号允许 96 位并包含点和冒号，新服务只允许 1–64 位字母、数字、下划线和短横线，首位为字母或数字。应生成独立服务编号并保存映射，避免直接沿用任意硬件编号。

队友的 Kotlin 文件是未编译验证的调用示例，需适配项目；其阻塞请求不会随协程取消立即中断。实现时应让网络请求和轮询可取消，并继续校验本地世代。当前服务没有取消任务 API：手机停止等待后服务仍可能处理旧任务，但结果不得影响新 A 或重新触发 B。

## 部署与联调前提

- 提供手机、眼镜可访问的 OCR 服务地址及 Bearer 令牌；局域网联调用电脑 IP，不能用手机自身的 `127.0.0.1`。
- 压缩包未证明新接口已部署到既有 Render 服务。要先验证新接口的 `/health` 返回 `ready:true`；原服务健康成功不代表 OCR 已可用。
- 包内已验证运行环境为 Windows x64 / Python 3.11 / CPU，首次依赖安装需要联网；部署说明建议全英文模型路径。现有 Render 环境的系统、内存、依赖与存储是否满足，需另行验证。
- 固件需支持拍照、Wi-Fi、原始 JPEG PUT、认证及新任务字段。本次没有板端源码，尚不能据此完成硬件修改。
- 服务保存图片和 SQLite 任务；生产使用的存储位置、保留时长和清理由部署方确定。

## 检查证据与验收

本次直接读取 ZIP，并按其最终 manifest 校验了 47 个文件，大小与 SHA-256 全部一致；未执行包内脚本。队友附带报告记录两张合成日期图真实 OCR 约 6.4–6.6 秒，报告未做真实药盒充分验证或 Android 编译/真机验收。包内明确记录的布局排序问题仍在，打包不意味着识别准确率已改善。

接入验收应包括：真实药盒生产日期/有效期、不同面单独拍摄、模糊图与无标签、多个候选冲突、错误令牌、202 但任务失败、旧 task/frame 上传、重复传图、服务未就绪、断网原编号恢复、新 A 抢占旧识别，以及全过程不触发旧 B。APK 编译成功只能证明软件构建，不能替代这些联调。
