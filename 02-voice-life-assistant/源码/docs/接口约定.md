# 手机、ESP32 与后端联调约定（0.6.2）

这份约定供 App、ESP32 固件和后端共同使用。当前架构为：**ESP32 录音 → BLE 发送 WAV → 手机离线转文字 → 按本机应用名称请求打开 / 按 App 内联系人请求拨号 → 本机存记录 → 可选后端同步文字记录**。后端不接收本流程的 WAV，也不参与这些手机指令的识别与执行。

APK 内置 Vosk 中文模型 `vosk-model-small-cn-0.22`，Vosk Android 0.3.47 + JNA 5.13.0。首次识别会准备本机模型，无需请求图片接口。手机接收、识别、执行与事件同步分别显示状态，失败主要用页面文字和震动反馈，不自动弹出识别错误框。

## 1. 首选：直接通过 BLE 发送完整 WAV

ESP32 将录制完成的 WAV 文件**从第一个字节到最后一个字节，按顺序通过 Notify 发送**，每次通知长度遵守实际 BLE MTU。手机拼接文件，收齐后本地解码和离线识别。**无需 JSON、Base64 或 audio_start/audio_end 消息。**

- 文件以 `RIFF` 开头，第 8–11 字节为 `WAVE`。第 4–7 字节是小端 RIFF 长度，完整字节数为该值加 8；App 靠它判断是否收齐，不靠发送停顿猜结束。
- 请先完成录音并回写文件头，再发送。长度必须准确，不接受 0 或 `0xffffffff` 占位的流式头；必须有合法的 `fmt `、非空 `data` 数据块，块长度及奇数长度后的填充也须正确。
- 单文件最大 10 MiB（10,485,760 字节），本地识别时长上限 180 秒。推荐每条指令 2–8 秒，16 kHz、单声道、16 bit 整数 PCM WAV。
- 本地解码接受整数 PCM（WAV 编码 1），单/双声道，8–48 kHz，8/16/24/32 bit；内部转为 16 kHz 单声道供识别。浮点、压缩 WAV 及 mp3/m4a/aac/webm 不属于本版离线识别支持范围，改文件后缀不能转换编码。
- 不要在 WAV 中混入日志、JSON、另一段录音或其他字节。内部音频恰好含换行、花括号、`RIFF` 等字节时仍按录音内容处理。
- 文件收齐并经过接收层结构检查后，App 分配 `wav-...` 事件编号，回 `ack / audio_received`，随后做本地解码、识别与执行；收到 `audio_received` 不等于已经识别成功。处理结束回 `result`，编码不支持等错误也通过结果反馈。
- 原始字节流没有包序号或额外校验和，不能检出所有损坏；固件须保证有序、完整发送。**等待上一段处理完成，并让助手回到前台后再发下一段**，识别忙碌时新录音会拒绝处理。
- 断开连接或连续 30 秒没有新数据，未完成录音会清理。重传需重新从完整文件开头发送，不上传或识别半段文件。

页面日志应包含“直接收到 WAV 文件”“录音接收完整”“手机转写完成”，然后显示动作结果。此时 WAV 不会发送后端。

## 2. 兼容：JSON 封装录音

直接发送 WAV 时无需使用这一节。旧固件仍可经 Notify 发送 UTF-8 JSON 对象，建议对象后加换行。完整对象即使没有换行也可解析；支持连续对象和 UTF-8 中文跨包。较长对象仍必须按 BLE MTU 拆成多次 notification。每段录音使用唯一 `id`，所有消息带 `v: 1`。

单个 JSON 上限 4 MiB（4,194,304 字节，包含字段）；超过 64 KiB 的未完成消息会暂存缓存文件，解析在接收线程执行。它不是单次 BLE 通知容量。超限或坏 JSON 会丢弃到下一个换行，可发送换行或重新连接恢复；当前接收器另有独立的原始 WAV 识别路径，并不是把裸 WAV 当成 JSON。

### 分块录音

开始消息指定完整文件的字节数：

```json
{"v":1,"type":"audio_start","id":"rec-0001","data":{"format":"wav","size":12480}}
```

WAV 原始字节分块，**每块独立 Base64 编码**。`index` 必须从 0 连续递增，推荐每块原始音频 4–64 KiB。单块 Base64 上限 3 MiB（3,145,728 个 ASCII 字符），整条 JSON 仍在 4 MiB 内。不要随意切开完整 Base64 字符串后当独立块解码。

```json
{"v":1,"type":"audio_chunk","id":"rec-0001","data":{"index":0,"base64":"..."}}
```

结束消息中的 `chunks` 等于实际块数；组装文件长度必须等于 `audio_start.size`：

```json
{"v":1,"type":"audio_end","id":"rec-0001","data":{"chunks":1}}
```

接收边写临时文件，单段最多 10 MiB。ID 不一致、乱序/丢块、Base64 无效或大小不符则拒收；30 秒无数据、连接断开时清理。只有收到合法 `audio_end` 且文件完整后，才进行本地识别。

**本版 JSON 录音只接受 `format: "wav"`**，其他扩展名在开始阶段就会拒绝；实际文件也必须是上节所列整数 PCM WAV。旧固件不要再发 mp3/m4a/aac/webm，改字段或文件后缀也不能转换音频编码。

### 一条完整短录音

`audio_ready` 可携带完整文件。`format`、准确的解码后字节数 `size`、标准 Base64 `base64` 都必填；该 JSON 仍须按 MTU 分多次 notification。

```json
{"v":1,"type":"audio_ready","id":"rec-0002","data":{"format":"wav","size":160044,"base64":"...完整 WAV 文件的 Base64..."}}
```

Base64 上限仍为 3 MiB，约对应 2.25 MiB 原始音频；更大文件使用分块方式，整段仍限 10 MiB。只发送手机无法访问的文件名或路径不会读取录音。`image_ready` 当前只记录媒体信息，不上传或识别图片；摄像头图片继续走朋友既有视觉上传协议。

### 去重、保留和重试

分块开始回 `ack / audio_started`，完整接收回 `ack / audio_received`，本机识别/执行结束后回 `result`。一次只处理一段，不要连续挤入多段。

JSON 事件按 BLE 设备和 `id` 保留最近 256 个编号，已收到的事件回 `ack / duplicate` 而不重复执行。直接 WAV 没有硬件事件编号，每次完整重发都会分配新编号，没有这项去重保证。

App 仅保留最近一段完整录音到私有目录，供试听和手动重新识别，新录音替换旧录音；不做音频持久队列或自动音频重试。**手动重试使用新编号，直接执行识别出的指令，可能再次拨号，不再弹出二次确认。**本机事件记录的重试队列与这段录音是两回事。

只有在助手前台开始识别，且结果返回前一直满足前台与同一 BLE 会话条件，才执行。后台收到、识别期间离开前台，或断开/切换设备时，转写可保存，但迟到指令不执行；中途回到助手也不会补执行旧指令，应重新发送。

## 3. 手机本地识别和执行

识别文字在手机完成，不需要后端返回 `transcript`。先保存 `audio_transcription` 记录，再判断能否执行。Vosk 平均词分值达到 0.65 才允许执行；分值未知/过低时只反馈“没有听清”，请重新说话。这不是准确率承诺，口音、噪声及联系人称呼仍可能被识别错。

只匹配完整、明确的支持指令，例如“打开 QQ”“启动微信”“打开抖音”“给女儿打电话”。打开应用时，通过 Android 真实的 `MAIN / LAUNCHER` 启动入口读取本机应用名称，唯一匹配后请求启动，不再把抖音包名写成唯一目标；新增软件不需要逐个录入包名或增加一条命令。应用需已安装、对助手可见，并具有可用启动入口。名称找不到、同名对应多个不同软件或应用目录读取失败时停止并反馈，不猜选。

电话称呼必须与 App 已保存的称呼完全一致，不读系统通讯录，不用近似姓名猜选号码；识别成其他内容、否定或混合长句不强制映射为动作。当前不包含在 QQ / 微信等 App 内发消息、视频通话或任意跨 App 连续操作。应用名称的转写仍可能受英文、口音和噪声影响，应分别检查转写文字和名称查找结果。

拨号使用 `CALL_PHONE` 权限及 `ACTION_CALL`，已授权后直接发起。打开普通已安装应用不需要逐个向目标 App 请求“允许打开”，也不需要无障碍权限。文字测试与硬件语音一样直接执行，不额外增加 App 二次确认框。

首次进入本版提供集中权限引导：一次发起基础权限申请，Android 12 及以上申请 BLE 附近设备权限，Android 11 及以下按系统要求申请位置权限，另申请直接拨号所需电话权限。系统仍可能分别询问，必须由用户或家人确认，App 不能代点“允许”。可以跳过，之后从设置重新打开引导；不要求开启手机麦克风、通讯录或无障碍权限。蓝牙开关、旧系统位置信息开关和默认 SIM / 双卡选择仍按系统规则设置，不能由 App 统一消除相关提示。

需要前台、解锁测试；没有后台 / 锁屏自动控制保证。打开其他 App 后，回到助手再发送下一条指令；页面不放语音或拍照按钮，不等于已实现后台持续保活。

结果以手机文字和震动反馈，不向硬件下发语音。成功请求操作时短震，失败或需注意时双短震；不支持震动时使用短暂文字提示。震动只表示 App 处理了结果，不表示电话已接通或对方已看到内容。

## 4. 最小 BLE 双向连通测试与结果消息

默认使用 Nordic UART Service：

| 用途 | UUID |
|---|---|
| Service | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` |
| 手机订阅 Notify | `6e400003-b5a3-f393-e0a9-e50e24dcca9e` |
| 手机回写 Write | `6e400002-b5a3-f393-e0a9-e50e24dcca9e` |

真实固件如用不同 UUID，应在 App“设备连接设置”填写实际值。手机通过 Write 回 UTF-8 JSON 行。

ESP32 发送：

```json
{"v":1,"type":"ping","id":"boot-1"}
```

手机先回 `ack / received`，再回：

```json
{"v":1,"type":"result","event_id":"boot-1","status":"pong","reply":"手机回传成功"}
```

随后可发文字消息验证手机动作：

```json
{"v":1,"type":"command","id":"cmd-1","text":"打开抖音"}
```

这只验证 BLE 文字通道和执行，不替代 WAV 识别测试。

回传统一字段为 `v`、`type`（`ack` 或 `result`）、`event_id`、`status`、`reply`，例如：

```json
{"v":1,"type":"ack","event_id":"wav-手机分配的编号","status":"audio_received","reply":"完整录音已收到，手机正在离线识别"}
```

常见结果 `status`：`intent_requested` 表示已请求系统打开/拨打，不是通话成功；`unsupported` 表示不支持的指令；`contact_not_found` 表示 App 内没有对应联系人；`app_not_found` 表示没有找到该名称的可启动应用，`app_ambiguous` 表示同名对应多个不同软件，`app_catalog_failed` 表示读取本机应用目录失败；`permission_denied`、`unavailable`、`busy` 为其他执行条件问题；`audio_invalid`、`transcription_failed`、`low_confidence` 为录音接收/识别问题；`not_executed` 表示本次未执行（例如迟到结果）。0.6.2 的名称查找不再返回原先抖音专用的 `app_not_installed`。固件应展示/记录 `reply`，不要把所有 `result` 都当作成功。

## 5. 后端：仅接收事件 JSON，地址单独确认

2026-10-23 已只读核对 `http://192.168.1.17:8000/health` 及 `/openapi.json`：服务在线，但 `POST /analyze` 要求 `image` + `intent`，是图片接口，响应为 `action/app_name/target/confirmation_required/message`。保留它供朋友的视觉功能使用；本版不发 WAV 给它，也不再要求新增语音识别服务。

**目前尚未拿到真实的事件存储接口。**在 App“后端记录存储（可选，不参与识别）”留空地址，记录会保存在本机 SQLite。朋友实现事件接口后，才填写完整 URL；以下 `/v1/events` 是本项目测试服务提供的路径，不代表朋友的 8000 端口已经有该路由。

```text
POST <朋友实际提供的事件存储完整 URL>
Content-Type: application/json; charset=utf-8
Authorization: Bearer <token>    # 只在配置了令牌时发送
```

请求示例：

```json
{
  "v": 1,
  "record_id": "67d624b2-cb91-4125-983b-5f144550107b",
  "event_id": "wav-09b752a4-6c2d-4595-b3f9-61caee52cc3b",
  "device_id": "elder-demo-01",
  "source": "local_asr",
  "type": "audio_transcription",
  "text": "给女儿打电话",
  "result": "transcribed",
  "occurred_at": "2026-10-23T06:20:00Z",
  "data": { "engine": "vosk-small-cn-0.22", "confidence": 0.91 }
}
```

| 字段 | 含义 |
|---|---|
| `v` | 协议版本，当前为整数 1 |
| `record_id` | 单条记录唯一编号；重试保留同一编号，服务据此幂等保存 |
| `event_id` | 指令/录音编号；同次转写和动作结果可用它关联 |
| `device_id` | App 配置的设备编号，不等同已实现用户登录或账户鉴权 |
| `source` | 来源，例如转写 `local_asr`、硬件音频动作 `ble_audio`、文字测试 `debug_text` |
| `type` | 类型，例如 `audio_transcription`、`audio_transcription_failed`、`action_result` |
| `text` | 手机识别/收到的文字；失败时可为空 |
| `result` | 该条状态，如 `transcribed`、`intent_requested`、`low_confidence` |
| `occurred_at` | 手机生成的 UTC ISO 8601 时间 |
| `data` | 附加 JSON 对象，例如引擎、分值、错误；不包含 WAV 文件 |

一段录音可能生成转写记录和动作结果两条，`record_id` 不同、`event_id` 相同。后端应按记录编号去重，不能只按事件编号丢掉后一条。`action_result.result: "intent_requested"` 不能解释成“已经接通电话”。

服务完成保存后，返回 HTTP 2xx JSON：

```json
{"ok":true,"record_id":"67d624b2-cb91-4125-983b-5f144550107b"}
```

`record_id` 必须与请求完全一致。空响应、非 JSON、错误编号、重定向或只有 HTTP 200 都不会标记成功。重复请求应幂等确认同一条已保存记录；写数据库成功后再确认，避免手机误以为已存储。

记录先写本机 SQLite outbox，再异步 POST；网络失败保留待同步，正常动作不等待后端。前台会重试，也可手动保存设置/同步；每批最多 20 条。记录接口为空时仅留本机，不会误发到图片接口。App 数据被卸载/清除后，本机记录也会丢失；不能把本机队列当作云端备份。

本项目的 `node server/demo-server.mjs` 可用于独立存储联调：默认 `http://电脑IP:8787/v1/events`，JSONL 文件持久化并按 `record_id` 去重，浏览器打开根地址可看最近记录。它不是图片服务、ASR 服务或完整的账户后台。

## 6. 网络与联调边界

WAV 离线识别和手机动作不需要后端网络。只有同步记录、视觉功能需要访问相应服务器。

局域网存储联调时手机和后端电脑需在互通 Wi-Fi/热点，使用电脑当前 IPv4；服务监听 `0.0.0.0`，端口允许入站。先用手机浏览器打开实际健康检查地址，开发电脑能访问不等于手机能访问。`192.168.1.17` 是局域网地址，换网络可能变化，不是公网部署地址。

0.6.2 的构建、静态检查及单元测试结果以 [功能与验证](0.6.2功能与验证.md) 为准，不沿用旧版本的测试数量。此前用桌面原生模型做过合成中文语音验证，但没有连接真实 Android 手机或 ESP32。仍须现场分别核验模型加载、BLE WAV 人声、按本机名称打开应用、手机拨号和事件落库，不把收到 `ping`、本机测试通过或 HTTP 在线当作全链路完成。
