> 面向接手整合的 agent 及 Android、固件、后端开发者。整理日期：2026-10-25（北京时间）。基线：当前工作区源码 `0.8.0 / versionCode 21`。
>
> 本文依据源码、构建配置和已有验证文件整理。本次仅新增交接文档，没有改业务代码、重新构建 APK、部署服务或执行真实设备验收。文中的“已实现”表示代码存在；测试、部署、实机结果分别说明。

## 1. 接手先看这里

**按钮交互补正：用户已确认 A、B 是两个独立实体按钮，不存在业务抢占关系；一般不会同时触发，同时出现也不应仅因另一个按钮触发而取消请求。现有 0.8.0 源码/安装包仍有 A 取消 B 的旧调度实现，合并时须对齐此差异。本文及历史材料里的抢占描述仅代表旧实现，不作为目标设计。专项说明见《硬件语音通信与手机权限控制链路_0.8.0.md》。本次仅修正文档，没有修改 APK。**

这是一个 Android 手机承接智能眼镜输入的生活助手 Demo。眼镜/ESP32 经 BLE 传入语音或识别文字；手机负责本地 ASR、A/B 任务调度、系统操作、视觉接口调用、结果显示与 TTS、本地记录及可选同步。

- **A 是用户主动指令**：打开真实已安装应用、拨打 App 内保存的联系人、系统导航、读文字/识别物体；可选接入自然语言意图代理。
- **B 是手机页面帮助**：用户授权本次观察后，检测页面停留，询问目标；模型建议一个真实控件，用户再次确认后点击一次，再检查结果并停止。
- **A/B 是两个独立按钮，不定义抢占关系**：旧实现会在新 A 时使旧 B 的提示、录音、网络结果、候选及确认失效，这是与目标约定不一致的部分。对齐时保留各自任务有效性、确认及执行前检查。
- **NextAction 是独立可选模块**：不是 A 意图接口，也不是 B 模型接口；不要把三套请求/响应互换。
- **当前主视觉集成是 `MedicineVision*`**：OCR 异步任务 + 独立同步物体识别。同路径的旧“统一视觉协议”还在代码里，字段并不等价。
- **固件和完整视觉后端没有在本工作区提供可直接构建的完整实现**。Android 的协议支持不能视为另外两端已经完成。

建议先读本文，再按需要查看具体源码。历史 README 和版本文档保留了旧能力、旧限制及旧协议；与本文冲突时核对当前调用路径和测试，不直接拼接旧说明。

## 4. 运行结构与边界

```text
眼镜 / ESP32
  └─ BLE Notify → BleClient → BleIncomingStream
       ├─ A 文字帧 v1 → 跳过手机 ASR
       ├─ 完整 WAV → OfflineSpeechClient / Vosk
       └─ JSON 分块 WAV/PCM → BleAudioTransfer → Vosk
                              ↓
                      AssistRuntime / AssistSession
                       ├─ A 本地指令 → Android 系统能力
                       ├─ A 云端意图 → b_agent_proxy → 单个 intent → 手机确认/执行
                       ├─ A 视觉 → MedicineVisionWorkflow → 外部视觉服务
                       └─ B 页面帮助 → BAssistController → BAssist → 模型代理
                                                               ↓
                                               用户确认 → 校验当前页面 → 点击一次

状态/结果 → HomeActivity JS 桥 → 本地 HTML 首页
         → 手机 TTS / BLE JSON 结果
         → SQLite events.db → 可选事件 HTTP 接口
```

`AssistRuntime` 持有 BLE、ASR、当前任务、视觉流程和业务配置；`VoiceForegroundService` 承载后台硬件连接。Activity 销毁不能直接等价为停止硬件服务。`HardwareConnectionController`、`HardwareReconnectPolicy`、`HardwareRestoreReceiver` 负责记住设备、重连及恢复尝试。

`AssistSession` 在 Android 主线程串行调度；`generation`、连接代际及各客户端 ticket 共同拦截旧回调。接手 agent 应优先复用这些入口，不新增绕过它们的“直接网络结果执行器”。B 与 NextAction 也不能同时争用执行权。

## 5. A 指令链路

### 5.1 本地优先

入口主要是 `AssistRuntime.executeA`，不是 Web 页面模拟按钮。

1. 先处理属于当前 `prompt_id` 且未过期的 A 应答。
2. 明确打开应用：从本机 Launcher 目录唯一匹配，使用真实启动 Intent；同名歧义停止，不猜包名。
3. 明确拨号：只使用 App 内保存的联系人。精确匹配按既有流程直接请求拨号；同音/多个候选需选择确认。
4. 返回、桌面、最近应用等明确导航优先走本地；页面操作/退出建议按当前流程确认。
5. 视觉问题进入视觉链路；其他未解析输入可进入可选 A 云端理解。未启用或缺配置时不能假装已完成。

同音匹配为有限能力，依赖 Android 拼音支持；API 29 以下或不可用时回退精确匹配。应用启动成功只代表系统接受启动请求，拨号成功只代表发出系统通话请求，不代表已接通。

### 5.2 A 云端接口

实现：`assist/ACommand*.kt`、`b_agent_proxy/command.mjs`。请求为纯文字与真实目录，不上传联系人电话号码。

```http
POST /v1/commands/interpret
Authorization: Bearer <自有代理令牌>
Content-Type: application/json
```

```json
{
  "version": 1,
  "task_id": "a-001",
  "utterance": "帮我打开微信",
  "apps": [{"id": "com.tencent.mm", "label": "微信"}],
  "contacts": [{"id": "contact-1", "name": "女儿"}],
  "screen": null
}
```

`screen` 可为 `{"package_name":"com.example.app","controls":[{"id":"next","label":"下一步","actions":["click"]}]}`，必须来自本次真实页面。成功响应：

```json
{"version":1,"task_id":"a-001","intent":{"type":"open_app","target":"com.tencent.mm"}}
```

| intent.type | 字段和语义 |
| --- | --- |
| `open_app` / `call_contact` | `target` 必须是本次目录内 ID |
| `navigate` | `target` 为 `back` / `home` / `recents` |
| `exit_app` | `target` 必须等于本次前台包名；只是回桌面，不强杀进程 |
| `screen_action` | `target` 为本次控件 ID；`action` 为该控件允许的 `click` / `scroll_forward` / `scroll_backward` |
| `vision` | `mode` 为 `OCR` / `OBJECT` / `COMBINED` |
| `clarify` / `unsupported` | `message` 为说明或澄清问题 |

协议限制：最多 500 应用、100 联系人、80 控件；原问题最多 2000 字符且不含控制/格式字符；请求 ≤128 KiB、响应 ≤64 KiB；手机整次 HTTP 超时 20 秒，代理 A 上游约 18 秒。响应严格拒绝多余字段、重复 JSON 键、错误 task_id、虚构目标和非法动作。仅返回一个 intent，不能替换成多步操作列表。

执行侧保留用户确认、有效期、当前任务/页面检查和一次执行闸门。A 的本地快速路径与云端建议的确认规则不同，不能笼统改写成“所有 A 都自动执行”或“所有 A 都必须确认”。

## 6. B Agent 链路

主路径：`BAssistController` → `com.bagent.android.BAssist` / `AndroidAssistPort` → `BAssistEngine`。

启用 B、开启无障碍并同意本次观察后，主工程用 `PageDwellDetector` 观察页面，默认停留约 25 秒；不直接启用原上游的重复点击/页面往返自动触发逻辑。之后询问目标、发送当前截图与页面控件、提出一次点击、等待本次确认、重新观察并执行一次，最后反思结果并停止。

模型接口是 `POST /v1/chat/completions`，`stream:false`，JPEG 通过 `image_url.url = data:image/jpeg;base64,...` 发送。模型固定 `Qwen/Qwen3-VL-8B-Instruct`；自有代理支持一或两张 JPEG，分别用于当前观察/结果检查等阶段。

`BModelProtocol.response` 要求单条 choice、`assistant`、`finish_reason=stop`，拒绝工具调用、拒绝响应及截断结果。模型阶段采用有序标题格式：规划通常为 `Thought/Plan`；目标动作阶段必须是 `Thought/Action/Description`：

```text
### Thought ###
选择本次目录中符合目标的控件。
### Action ###
{"action":"click","target_id":3}
### Description ###
建议点击下一步，等待用户确认。
```

`target_id` 是本次手机提供的整数编号；手机绑定真实控件及坐标。**当前 B 建议主路径只接受一次 click**，不接受模型猜坐标、任意自然语言操作、滑动/返回/输入或多步脚本。工程里存在通用滚动/返回执行工具及旧坐标解析器，不代表 B 主链路已经开放这些能力。

取消、拒绝、锁屏、换页、滚动、断线、超时、撤销观察同意和 A 抢占均应阻止旧建议执行。尤其不要把 `choices[0].message.content` 直接当可执行 JSON；还必须经过阶段格式、真实目标及确认检查。

## 7. 视觉接口：当前协议和旧协议必须分开

### 7.1 当前交接服务（medicine-v1）

配置入口：“设置 → A/B 页面帮助配置 → 交接视觉服务器”。根地址不带 `/docs` 或 `/api/v1`；现有文档给出的服务为 `https://ai-glasses-backend-7bj3.onrender.com`，本次未联网核验部署状态。

主要实现：`MedicineVisionApiClient.kt`、`MedicineVisionWorkflow.kt`。除健康检查外使用 `Authorization: Bearer <VISION_API_TOKEN>`。整个视觉任务共用 180 秒预算，当前业务流程使用单张 `f0`。

| 步骤 | 接口与关键约定 |
| --- | --- |
| 健康检查 | `GET /health`；需 `ready:true` 及对应 capability：`ocr` / `object_recognition` / `mobileagentb_proxy` |
| 创建 OCR | `POST /api/v1/vision/tasks`；`task_id`、`source_button:"A"`、`task_type:"medicine_ocr"`、`expected_frames:1`、`question`、可选 `record_id` |
| 上传图片 | `PUT /api/v1/vision/tasks/{task_id}/frames/f0`；正文为原始 JPEG，`Content-Type:image/jpeg`，不是 multipart/Base64；附 `X-Task-Id`、`X-Frame-Id` |
| 补充问题 | `PATCH /api/v1/vision/tasks/{task_id}`，JSON `{"question":"..."}` |
| 查询 OCR | `GET /api/v1/vision/tasks/{task_id}`，约每秒查一次，受总预算限制 |
| 物体识别 | `POST /api/v1/object-recognition`；同步 JSON 请求/响应，不走异步结果轮询 |
| B 模型 | 服务若声明提供，可用其 `/v1/chat/completions`；手机 B 配置仍单独保存 |

OCR 识别状态集合为：`awaiting_question`、`awaiting_frame`、`queued`、`running`、`succeeded`、`failed`、`timed_out`、`expired`。成功答案支持根层或 `result` 中的 `answer`、`evidence_text`、`review_required`；两处同时出现时需一致。`review_required` 缺省按 true 处理，尤其药名、日期、剂量必须提示核对。

物体识别请求和响应最小样例：

```json
{"task_id":"vision_001","question":"这是什么？","images":["data:image/jpeg;base64,<本次JPEG>"]}
```

```json
{"task_id":"vision_001","status":"succeeded","answer":"图片中是一个杯子。","evidence_text":"由本次图片识别。","review_required":true}
```

客户端底层允许 1–4 张图，每张 JPEG ≤8 MiB，物体请求体 ≤48 MiB；当前 workflow 固定单张，不代表 UI 已实现多图。`COMBINED` 是手机协调同一张图先 OCR、再物体识别并合并结果，不是要求服务新增 `COMBINED` 任务类型。

服务返回 mock/模拟结果、错误 task_id、非成功状态或错误类型的答案字段不会被当作真实识别答案。创建/上传失败不盲目重发；OCR 可保存原编号恢复查询，恢复时不能重新上传或换问题冒充同一任务。

### 7.2 眼镜拍照的实际依赖

手机生成两个不同层次的 ID：A 硬件任务 `task_id` 和服务任务 `vision_task_id`。下行示例：

```json
{
  "v": 2, "type": "capture", "source_button": "A",
  "task_id": "a-001", "vision_task_id": "vision_001",
  "event_id": "rec-a-001", "frame_id": "f0", "mode": "OCR",
  "question": "请读一下文字",
  "upload_url": "https://your-vision.example/api/v1/vision/tasks/vision_001/frames/f0",
  "upload_method": "PUT", "upload_owner": "esp32",
  "upload_headers": {
    "Authorization": "Bearer <视觉服务器令牌>",
    "X-Task-Id": "vision_001", "X-Frame-Id": "f0", "Content-Type": "image/jpeg"
  }
}
```

OCR 模式可由眼镜直接 PUT JPEG，手机轮询结果。OBJECT 模式没有当前协议提供的图片托管上传 URL；手机发 `return_image_url:true`，固件/服务必须另行提供本次可读取 JPEG。COMBINED 除 OCR 上传外也需把同一张照片返回给手机用于物体请求。

固件回传 `image_ready` 时，在 `data` 中带正确 `task_id`、`vision_task_id`、`frame_id:"f0"` 及 `url` 或 `image_url`。手机用 `TaskPhotoDownloader` 校验配置服务源并下载；不支持直接 BLE 原始 JPEG，不使用 `latest` 缓存替代当前图。

**当前主要缺口：OBJECT 的照片托管/可读 URL 合同以及真实固件配合。**不能假定上面的 OCR PUT 地址在 OBJECT 也存在，不能把“上传成功”当作“手机已取得照片”。优先先验收手机选 JPEG 的服务通路，再验收眼镜全链路。

现协议会把自有视觉服务上传令牌经 BLE 下发给眼镜，尚无任务级短时上传票据；第三方模型 Key 不下发。其他板块若引入上传票据，需要同步修改固件、capture 字段、客户端和后端鉴权。

### 7.3 保留的旧路径

`AssistRuntime.startVisualQuestion` 的优先级为：启用交接服务 `medicineEnabled` → 启用旧统一视觉 `unifiedVisionEnabled` → 旧 OCR / multipart 视觉分支。

- `VisionApiClient` / `VisionWorkflow`：0.7.8 旧统一视觉任务，同样出现 `/api/v1/vision/tasks`，但契约不同；不能只凭 URL 相同就混用。
- `OcrApiClient` / `OcrWorkflow`：早期 OCR 兼容路径。
- `VisionClient`：旧 `/vision/analyze` 与 `/analyze` multipart 分析，后者需要图片和 intent。

合并时明确选定契约及功能开关。新服务若只实现 OCR 和 object-recognition，不应靠打开旧开关“试通”。

## 8. BLE / 固件对接

默认 Nordic UART，可在手机设置按实际固件修改：Service `6e400001-b5a3-f393-e0a9-e50e24dcca9e`；Notify（板→手机）`6e400003-b5a3-f393-e0a9-e50e24dcca9e`；Write（手机→板）`6e400002-b5a3-f393-e0a9-e50e24dcca9e`。Write 需支持带响应写入；不能用系统配对代替 GATT 订阅。

### 8.1 录音 JSON v2

UTF-8 JSON 行，以换行结束；BLE 通知是流片段，不等于完整 JSON。A 开始录音应立即发事件，使手机立即清理 B：

```json
{"v":2,"type":"button_start","id":"rec-a-001","data":{"session_id":"boot-001","task_id":"a-001","source_button":"A","purpose":"command"}}
```

结束后发同一录音 ID 的 `recording_meta`，保留上下文并补真实 `format` 和 `size`；收到匹配的 `ack/status=ready_for_audio` 后才发送完整 WAV，或以下 JSON 分块流程：

```json
{"v":2,"type":"audio_start","id":"rec-a-001","data":{"format":"pcm_s16le","size":32000,"sample_rate":16000,"channels":1,"bits_per_sample":16}}
{"v":2,"type":"audio_chunk","id":"rec-a-001","data":{"index":0,"base64":"<该块字节的Base64>"}}
{"v":2,"type":"audio_end","id":"rec-a-001","data":{"chunks":1}}
```

示意 size/chunks 必须替换成真实值。分块 index 从 0 严格连续，最终字节数和块数一致，不允许丢包、重复、乱序或两份音频交错。

推荐 16 kHz、单声道、16-bit 小端整数 PCM、2–8 秒。JSON PCM 要明确 `pcm_s16le` 及采样参数；允许 8–48 kHz、1/2 声道、16 bit，手机补 WAV 头后识别。完整 WAV 上限 10 MiB / 180 秒，业务录音等待约 90 秒；这些上限不代表建议录满。任意裸 PCM、AAC/MP3、未知固件二进制音频帧未适配。

标识符按协议通常为 `[A-Za-z0-9._:-]{1,96}`。每次开机换 `session_id`，每次新录音换 `event_id`/A `task_id`；重发同一事件不能换 ID 规避去重。

### 8.2 B 回答与 A 语音确认

B 必须先收到手机 `assist_prompt`，再使用手机给出的 `task_id`、`prompt_id` 发录音元信息：`source_button:"B"`、`purpose:"assist_reply"`。下一轮问题会换 prompt；旧回答不能批准新建议。

A 的确认/澄清由手机下发 `type:"a_clarification"`、`source_button:"A"`、`task_id`、`prompt_id`、`question`。固件在用户随后按 A 的录音元信息中原样回传本次 `prompt_id`，并使用新录音自身的事件/任务/会话 ID。无关联的“确认”不批准旧操作；旧固件请通过手机弹窗确认。

`assist_cancel`、取消、断线后应清空待发送 B 回答；新 A 开始时停止旧 JSON 音频。若旧裸 WAV 已开始传，不能在 WAV 字节中插入新 JSON，否则会损坏流。

### 8.3 A 文字帧 v1 兼容

硬件已识别文字时，发送原始二进制帧，不再运行手机 Vosk：

```text
A5 5A | version=01 | type=01/02 | seq:uint32LE | N:uint16LE |
lang:2 bytes | UTF-8 body:N bytes | CRC:uint16LE | 0D 0A
```

总长 `N+16`，N ≤1024；type 01 文字要求语言 `en`，type 02 状态要求 `--`。CRC 为 CCITT-FALSE（初值 FFFF，多项式 1021，无反射/末异或），覆盖偏移 2 起的 N+10 字节。固定 `open QQ` 样例：

```text
A5 5A 01 01 04 03 02 01 07 00 65 6E 6F 70 65 6E 20 51 51 85 19 0D 0A
```

连接内按 seq 去重；断线清空，不能保证跨连接去重。状态帧绝不执行指令。该版本没有 A/B 来源或 prompt，只能作为 A 新输入；不支持 B 回答及旧操作确认，也不应自行把语言字段改为 `zh`。重发请求走 Write 精确 ASCII `RESEND\n`。

仅最终文字或裸 WAV 时，手机不能知道物理按键何时开始；要展示并关联录音开始须实现 `button_start`。该事件不定义业务抢占；旧源码的取消逻辑需要按独立按钮约定核对。

## 9. 首页、记录和数据

### 9.1 首页 JS 桥

`HomeActivity` 加载 assets HTML，注入 `window.AndroidApp.postMessage(JSON.stringify(...))`；原生通过 `window.onNativeMessage(message)` 回传。

当前请求类型包括：`get_state`、`save_contact`、`open_debug`、`open_setup`、`repair_permissions`、`open_assist`、`scanHardware`、`connectHardware`、`disconnectHardware`、`startBackgroundHardware`、`stopBackgroundHardware`、`setAutoReconnect`、`openBackgroundSettings`、`openDiagnostics`。

请求使用 `type` 和 `request_id`；连接带 `address`，自动重连带 `enabled`，联系人保存带 `name`/`phone`。桥消息最多 4096 字符。响应主要是 `type:"state"` 或 `type:"result"`，后者含 `request_id`、`ok`、可选 `message`。

state 包含 contacts/records/lastResult、permissions、BLE 状态/设备/MTU/后台开关、voiceStage/voicePercent/收包字节及速度、transcriptText、asrReady、installedAppCount 等。整合新前端时保持这些字段和请求名，扩展后同步修改原生、HTML 与桥接测试。

浏览器直接打开根 HTML 时无原生桥，进入模拟演示；`VisualDemoActivity` 也是独立预览页，没有注入真实桥。模拟电话、定位通知或子女视图不能作为真实拨号、定位服务或多端同步的实现证据。

### 9.2 本地数据和事件接口

- `saved_contacts` SharedPreferences：`contact:<称呼>` → 电话；不读取系统通讯录。
- `assist_settings`：A、B、OCR、交接视觉、旧统一视觉、TTS 等独立配置。
- `app_settings`：旧业务/记录接口等设置。完整字段以各配置读取处为准，不直接复制其他手机的偏好文件。
- `BackendSync`：SQLite `events.db`，表 `events(id PRIMARY KEY,payload,created_ms,synced)`；本地先存，失败保留待上传，每批最多 20 条。

事件写入接口为独立配置的完整 URL；演示服务使用 `POST /v1/events`：

```json
{"v":1,"record_id":"record-001","event_id":"rec-a-001","device_id":"phone-001","source":"button_A","type":"action_result","text":"打开微信","result":"已请求打开微信","occurred_at":"2026-10-25T02:00:00Z","data":{}}
```

成功必须返回 2xx 且 `{"ok":true,"record_id":"record-001"}`；手机验证确认 ID 后才标记 synced。服务端以 `record_id` 幂等，同 ID 相同内容可确认重复，不同内容应冲突。不要把 `record_id`、录音 `event_id`、A task、vision task、B prompt 合成一个字段。

`server/demo-server.mjs` 用 JSONL 保存记录，并提供 `GET /v1/events` 和演示查看页；没有完整用户体系、家属端、设备绑定或生产数据库。记录同步失败不阻止本地动作。生产整合需另行确定账号/设备归属、访问控制、保留策略；不要把设备 ID 当用户认证。

## 10. 独立 NextAction 模块

保留 `nextaction/` 的 trigger、observation、domain、network、execution、diagnostics 分层。入口可来自 App、BLE COMPLETE 适配器或无障碍入口，但实际能否触发仍由当前宿主授权和路由控制；旧 COMPLETE 不应绕过 A/B 直接执行。

后端是 `agent_backend/`，`POST /api/v1/next-action/predict`。请求含 `schema_version`、UUID `request_id`/`capture_id`、当前页面、JPEG、真实节点、历史和候选；响应含同样 ID 及 `decision:{action,candidate_id,confidence,reason}`。动作枚举为 `TAP/SCROLL_UP/SCROLL_DOWN/BACK/NO_OP`，与 A、B 协议都不同。

服务端 mock 返回本次真实 NO_OP，App 本地 mock 用于安全练习。截图 ≤1 MiB、总请求 ≤2 MiB、节点 ≤160、候选 ≤40、历史 ≤20。一次请求仅一次预测，手机还需执行闸门。此前说明记录 HTTP 依赖/路由和真实部署未完整验证；本次没有重测该后端，不沿用 B 代理测试作为其验收结果。

## 11. 配置、权限和部署

### 11.1 配置彼此独立

`medicine_*`、`b_agent_*`、`a_command_*`、`unified_vision_*`、`ocr_*` 为独立设置。交接视觉配置中的 `useForB` 会把 B 地址设为该根地址加 `/v1` 并复制对应服务令牌；**不会自动配置 A 意图代理**。A/B 若部署到不同服务器，令牌也必须分别配置。

手机只填自有服务器访问令牌。第三方模型 Key 只在服务器环境变量。当前服务令牌存于手机 SharedPreferences，尚未实现正式用户身份鉴权或独立密钥存储方案。

新 A/B/视觉配置要求 HTTPS；调试版显式打开对应 LAN 开关后才允许私网 IPv4 HTTP，release 禁止明文。旧记录客户端接受 HTTP/HTTPS，其实际连通性还受 Manifest 限制；不能把新客户端的严格策略误写成所有旧客户端都完全一致。

### 11.2 Android 权限

BLE 需扫描/连接权限；Android 11 及以下需按系统要求检查位置权限和开关。拨号需 CALL_PHONE；Android 13+ 通知权限及 connectedDevice 前台服务用于后台硬件连接。BLE 音频文件转写不需手机麦克风；RECORD_AUDIO 用于手机麦克风调试路径。

截图/跨 App 单步操作需用户在系统单独开启 `NextActionAccessibilityService`，并遵守本次采集同意；API 26–29 不能因此宣称支持无障碍截图。没有新增悬浮窗权限来代替无障碍授权。华为后台管理仍需用户允许自启动/关联启动/后台活动；强行停止、撤权、锁屏和厂商限制仍影响运行。

### 11.3 Node A/B 代理部署

`b_agent_proxy` 无第三方 npm 依赖，package 要求 Node ≥22，部署建议 Node 24 LTS。Render Root Directory 指向该目录，Build `npm install --ignore-scripts && npm test`，Start `npm start`，Health `/healthz`。

环境变量：`SILICONFLOW_API_KEY`（服务端第三方 Key）、`B_PROXY_TOKEN`（另生成至少 32 字符代理令牌）、平台注入的 `PORT`。两个 POST 共用代理 Bearer 认证；固定模型 Qwen3-VL-8B-Instruct。`/healthz` 声明能力不等于上游模型和余额已可用。

代理源码、部署模板与文档存在，不代表线上已更新。接手方需核对部署版本，分别取得真实 A 意图和真实 B 截图调用结果，不在日志或交接文档中复制密钥。
