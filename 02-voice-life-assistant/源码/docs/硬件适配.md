# ESP32-S3-Korvo-2 V3.0 硬件对接（0.5.0）

参考资料：[Espressif ESP32-S3-Korvo-2 V3.0 官方指南](https://docs.espressif.com/projects/esp-adf/en/latest/multimedia-boards/dev-boards/user-guide-esp32-s3-korvo-2-v3.0.html)。

## 指南能确认什么

- 主控 ESP32-S3-WROOM-1 支持 Wi-Fi 和 Bluetooth LE。BLE 能传递数据，但指南不定义本项目的 GATT 服务 UUID、特征 UUID 或消息协议。
- 板载双麦克风，输入路径含 ES7210 多通道 ADC；ES8311 通过 I2S/I2C 连接，可配合功放和外接扬声器播放。
- 板上有摄像头连接器，摄像头是外接模组，不能仅凭指南假定包装一定含摄像头。
- 板卡具备音频能力，不等于固件已经生成正确 WAV；不能从板卡型号推断手机实际收到的采样率、位深、声道或 BLE 分包内容。

## 当前分工与链路

```text
麦克风 → ESP32 录制完整 PCM WAV → BLE Notify → 手机离线中文转写 → 本机指令执行
                                                        └→ 文字/动作记录 → 可选后端数据库
摄像头 → 原有 Wi-Fi 图片上传协议 → 朋友的视觉后端
```

手机内置 Vosk 中文模型，**录音识别不再依赖后端，不上传 WAV**。朋友原有 `http://192.168.1.17:8000/analyze` 继续用于图片，不能当作事件记录接口；真实事件存储 URL 尚待朋友提供，暂时可以不配。

目前反馈为手机页面文字和震动，不通过开发板扬声器播报。板上虽有播放硬件，但若以后需要播报，仍须另行实现音频下行、格式/分包、缓存和固件播放，不是打开现有权限就会自动具备。

## 硬件同学需要提供的信息

1. 实际 BLE 广播名、Service UUID、手机订阅的 Notify UUID、手机回写的 Write UUID；Write 是否支持 `WRITE` 或 `WRITE_NO_RESPONSE`。
2. 固件发送内容的真实样例：是否从 WAV 文件第一个字节开始；有无额外自定义包头、日志或序号；发送 MTU 和流控方式。
3. WAV 实际编码、采样率、位深、声道、时长及文件头是否在录制结束后更新准确。不要只说“WAV”，扩展名不能说明内部编码。
4. 固件如何处理手机返回的 UTF-8 JSON 行、`ack` 和 `result`；下一段录音的触发/等待方式，以及断线后是否从头重发。

默认 App UUID 为 Nordic UART Service：Service `6e400001-b5a3-f393-e0a9-e50e24dcca9e`、Notify `6e400003-b5a3-f393-e0a9-e50e24dcca9e`、Write `6e400002-b5a3-f393-e0a9-e50e24dcca9e`。如固件不同，在 App 设备连接设置填写实际 UUID。

## 推荐录音与发送方式

推荐 **16 kHz、单声道、16 bit 整数 PCM WAV，每条 2–8 秒**。本版解码支持整数 PCM 编码 1，单/双声道、8–48 kHz、8/16/24/32 bit；单文件最多 10 MiB，最多 180 秒。不支持压缩或浮点 WAV，也不对 mp3/m4a 等做本地解码。

先结束录音，回写 RIFF 文件长度和 `data` 长度；再通过 Notify 从头到尾按 MTU 顺序发送完整 WAV。首 4 字节为 `RIFF`，第 8–11 字节为 `WAVE`，完整文件长度等于第 4–7 字节小端数值加 8。App 由这个准确长度判断收齐，**无需 JSON、Base64、开始/结束消息**。不要在中间插入日志、消息或另一个文件。带自定义包头的固件需要按真实内容单独适配。

App 收齐后回 `ack / audio_received`，再本地识别并回 `result`。请等上一段完成、助手回到前台再发送下一段；识别忙碌时新录音不会排队。直接 WAV 没有固件事件编号，完整重发可能再次拨号，不能依赖 App 自动去重。30 秒没有新数据或断开连接会清理未完成数据，重发要从文件开头开始。

旧 JSON 的 `audio_start → audio_chunk → audio_end`、`audio_ready` 仍兼容，大小、序号、Base64 和事件 ID 规则见 [接口约定](接口约定.md)。0.5.0 只接受 `format: "wav"`，其他格式在开始阶段拒绝；实际文件还须符合上述 PCM WAV 编码。

## 现场按这个顺序核验

1. 手机允许必要 BLE 权限，填实际 UUID，搜索连接，确认已订阅 Notify。
2. ESP32 发 `{"v":1,"type":"ping","id":"boot-1"}`，确认收到手机的 `ack` 和 `result / pong`，先验证双向通道。
3. 手机上先保存一个测试联系人并授权电话，安装抖音完整版，单独用文字测试确认系统操作可用；会直接执行，不弹 App 二次确认。
4. ESP32 录制一段人声明显、无截断的“打开抖音”，发送完整 WAV。查看“接收完整 → 手机离线识别 → 识别文字 → 动作结果”。首次准备模型会额外等待。
5. 识别不清时试听 App 保留的上一段：先核对是否有人声、声道/采样率、噪声和 WAV 完整性。模型分值过低不会执行；分值也不能保证识别准确。
6. 用保存的准确称呼测试电话，例如“给女儿打电话”。手机解锁且助手前台；双卡默认通话 SIM 可预先设置。识别时离开前台或断线，迟到指令不会执行。
7. 前面的动作通过后，再单独验证文字记录同步与数据库保存；后端断网不应阻止本地识别。

当前尚未连接真实 Android 手机和 ESP32；文档中的手机/硬件步骤是待现场验证清单。纯 JVM 及 Windows 合成语音模型测试不能代替 BLE、真实老人语音或 Android 原生模型的真机结果。
