# 四人六小时联调分工（参考）

这是一份把现有 App、硬件、视觉服务、云端和数据库接起来的冲刺计划，不是六小时完成全部产品能力的保证。云端和数据库已有同学负责，本次先对齐、复用，避免重复搭建。所有时间都用于开发和联调，不含汇报准备。

目标是跑通两条真实链路：A 收到硬件语音后，直接操作手机或拍照问答；B 发现操作可能卡住后，提出建议，收到硬件语音确认，再重新查看页面并执行一步。

**两条业务独立，仍在同一个 APK 内。**收到录音前的来源标签就确定进入 A 还是 B；A 不明指令不转 B，B 不读取 A 的目标、不启动硬件摄像头。A 处理任务期间 B 暂停观察、推理和提示，结束后清理旧线索并冷却恢复。

## 四个人各负责什么

| 人员 | 主要工作 | 交给其他人的东西 |
|---|---|---|
| 1．硬件同学 | A/B 按键防误触、录音开始与结束、WAV 传输、相机拍照、接收手机回执 | 真机能收到的录音；音频属于 A 还是 B、对应哪个任务；可关联的照片或照片上传结果 |
| 2．Android 同学（你） | 按按钮来源分别处理 A/B、手机转文字、启动应用/拨号、后台接收、B 提示与口语确认、执行前重看页面、朗读与震动 | 可安装 APK；手机执行结果；发往云端的任务与记录 |
| 3．视觉同学 | 接相机照片、选择清楚的帧、图片/OCR/问题分析、返回可朗读的答案或重拍原因 | 真实照片对应的答案；失败时的明确状态；与原问题相同的任务编号 |
| 4．云端与数据库同学 | 对齐已有服务；任务关联、结果接口、记录存储；根据屏幕与操作摘要生成 B 帮助建议 | 手机可访问的地址、接口说明、成功/失败样例；真实保存记录；B 建议及编号 |

协作规则：硬件只认录音、照片和回执；Android 负责手机行为；视觉负责看图回答；云端负责服务与记录。让一个任务编号贯穿各端，出了问题就能找到卡在哪一段。

不用训练新模型，也不重复搭建两套语音模型。设备收发、转文字、日志工具可以复用，但 A/B 的目标、状态和处理规则分开。B 的四阶段固定为“采集近期操作 → 本地规则筛疑似困难 → 询问并用 B 澄清 → 确认一步、执行、停止”；数据库保存记录，不作为 B 即时判断的前置条件。

## 0–0.5 小时：冻结接口，检查真实设备

四个人一起用实际参赛手机、ESP32 和后端地址做检查。半小时内把下面的选择写进同一份接口说明，随后先保持不变。

- A/B 双击开始录音，录音中单击结束。确认防抖时间、最长录音时间以及忙碌时如何反馈。
- 音频格式固定；优先使用现有 APK 已支持的 WAV 编码与采样参数，发送一段真实录音验证。音频必须标明 A/B、录音编号和关联任务，不能只凭 WAV 内容猜来源。
- 当场用相同一句话分别从 A/B 发送，核对它们进入不同处理模块；来源不明时不猜。A/B 的任务编号与目标不能混用。
- 确定图片唯一通路：硬件 Wi-Fi 直传云端，或先给手机再由手机上传。不要同时开发两套；照片必须能关联到原来的语音问题。
- 确认手机能访问视觉、B 建议和记录接口。明确各自请求字段、成功/失败返回、超时，以及如何查结果；已有接口能用就沿用。
- 选定一台 Android 11 及以上测试机，家人或开发者先完成 BLE、电话和 B 所需无障碍授权；准备可识别的已安装应用及 App 内联系人。
- 选择 2–3 个没有私人信息的真实页面，用来验证可复用的屏幕观察和导航能力。示例只作为验收场景，不写成“只有女儿视频”之类的固定逻辑。

**第一关：** 手机收到一段硬件 WAV 并转出文字；手机访问真实接口得到有效返回；硬件接收到一次手机回执。任何一项没通，先修这一段，暂不接复杂模型推理。

## 0.5–2 小时：平行开发，先突破跨 App 接收

| 人员 | 这段时间做什么 |
|---|---|
| 硬件 | 跑通 A/B 录音及来源标记；补齐分片、结束标志和回执；准备重复发送、断线重发测试 |
| Android | 优先把 BLE、录音转文字和按来源分派从页面生命周期中分离，按系统要求做前台服务及常驻通知；A/B 分开保存任务状态；保留现有按安装名称启动应用、按本机联系人拨号的逻辑 |
| 视觉 | 用真实相机照片调用已有分析服务，返回问题答案；模糊照片返回重拍原因，不编造答案 |
| 云端与数据库 | 在手机上验证各接口可达；保证编号原样回传；记录可以查询，重复请求不重复创建业务记录；准备 B 建议返回样例 |

Android 是关键路径。**不要等所有界面完善后才测后台。** 在这一阶段就打开另一个应用，保持手机解锁，用硬件 B 发送录音，检查助手不在前台时能否收到并转写。这里只验证跨 App 接收与识别，不因“收到了”就宣布 B 全链路完成。

**第二关：** A 语音能分别启动至少两个手机已安装的应用；打开其他应用后仍能收到并处理下一段硬件录音；拨号用事先约定的测试号码验证，避免无意打扰。

若跨 App 接收没通，它就是当前最高优先级。可以继续完成其他独立模块，但只能记录“A 前台路径已通、B 跨 App 待通”，不能用返回助手后的演示替代 B 验收。

## 2–3 小时：跑通 A 的拍照问答

| 人员 | 这段时间做什么 |
|---|---|
| 硬件 | 接收拍照请求，拍摄并按约定通路上传；每次拍照回传相同任务编号 |
| Android | 语音判断为看物问题后发拍照请求；等候结果；用手机朗读答案并震动提示；记录原问题、答案与结果状态 |
| 视觉 | 从少量图片中先选清楚的一张，进行 OCR/看图回答；看不清或缺少对应文字时明确要求重拍 |
| 云端与数据库 | 关联语音问题、照片和答案；返回任务结果；确认数据库真实保存，记录失败不阻塞老人得到答案 |

先拍一张，质量不足再补拍，不必为了展示复杂度持续上传视频。必要时采少量帧做选图，先确认网络和处理耗时，再优化。

**第三关：** 老人通过硬件说一个真实看物问题 → 真拍照 → 云端返回该照片对应的答案 → 手机朗读 → 数据库查到同一任务。遮挡或模糊照片应得到“请重拍”，而不是错误答案。药盒只读可见文字；涉及具体服药决策时不能把识别结果说成医学判断。

## 3–4.5 小时：跑通 B 的最小帮助闭环

| 人员 | 这段时间做什么 |
|---|---|
| 硬件 | B 录音标明它回答的是哪个建议；无待确认建议时，B 作为主动请求帮助入口；验证确认、取消两种口语录音 |
| Android | B 独立保存无障碍短缓存及目标；发现反复点击/往返且页面无进展时请求建议；B 转文字后只结合 B 的问题理解确认、取消或补充；确认后关闭提示、重新采集页面、复核并最多执行一步；A 工作时暂停 B |
| 视觉 | 视觉链路回归；协助检查 B 截图是否清楚，但不要把硬件相机照片和手机屏幕截图混用 |
| 云端与数据库 | 根据当前控件、必要截图、近期操作摘要生成一个帮助建议；不确定时询问目标；接收确认/取消与执行结果记录 |

这一步不做全程录像，也不逐次点击都请求大模型。先在本地判断“可能卡住”，再按需发一次屏幕信息。可从“近 10 秒同一目标反复点击 3 次，页面关键内容未变化”等规则开始验证，参数现场调整；它只是触发线索，不是证明老人想做什么。

模型给出的是建议，不是可以直接执行的任意脚本。没有足够上下文时问“您想做什么？”，不要凭点击习惯断言“您要和女儿视频”。模型分数只能作为内部参考，不能宣传成经过验证的准确概率。

口语确认至少试“对，就这样”“不用了”“不是，我想……”三类。取消优先，不确定就不执行。用户确认后，必须重新看屏幕并定位目标；提示框出现前的坐标和候选不能直接沿用。先保留单步边界，能解释下一步并可靠停止，再考虑后续多步能力。

B 中说“我想和女儿视频”仍留在 B 澄清当前屏幕任务，不转 A 或开启硬件摄像头。B 不从 A 的上次命令猜目标，也不为了保存成功才开始处理口语回答。确认目标后若仍不清楚下一步做什么，应解释或补问，不把“大目标确认”当成连续操作许可。

**第四关：** 在真实页面上产生停滞信号 → 出现帮助建议 → B 录音口语确认 → 手机重新看屏幕 → 执行一个实际动作 → 检查页面是否产生预期变化并保存结果。再换一个页面验证同一套机制，而不是靠场景名称写分支。手机 API 接受点击不等于任务已经完成，结果要区分“已变化”“无变化”“无法确认”。

如果仅在 App 内练习页跑通，就如实记作“练习页闭环”，不能记作第三方 App 已可通用操控；如果只有主动按 B 才询问，不能记作主动停滞检测已完成。

## 4.5–6 小时：负例回归、打包、留恢复办法

四个人停止加新功能，按同一张清单复测。

| 检查 | 必须看到的结果 |
|---|---|
| A/B 误触、同一录音重复发送 | 不重复开启任务，不重复拨号或点击 |
| A 含糊语句或当前不支持的指令 | 在 A 内澄清或结束，不自动进入 B 预测 |
| B 已有线索或待回答时启动 A | B 暂停且旧建议作废；A 结束后清旧事件、冷却再观察 |
| B 回答明确手机目标或提及眼前物品 | 留在 B 屏幕帮助范围，必要时说明范围；不转 A，不开硬件摄像头 |
| A 打开不同应用、联系人不存在 | 按实际安装名称匹配；找不到就说明，不能随便打开或猜号码 |
| B 说“不用”“算了”“不是这个” | 取消或补问，不能因句子含肯定词就执行 |
| 确认前切换页面、目标消失 | 重看后拒绝旧动作，不按旧坐标点击 |
| 蓝牙断开、录音未传完 | 明确失败/可重试，不执行残缺内容 |
| 云端断网、超时、迟到结果 | 有结束状态；迟到结果不能触发过期建议 |
| 模糊照片、无对应文字 | 提示重拍或说明无法判断，不编答案 |
| 连续多次问答和操作 | 缓存有界，过期原始内容清除；数据库记录能关联到对应任务 |
| 记录接口失败后恢复 | 本地已完成动作不重做；仅按记录编号重试保存 |
| 进入其他 App 后再用硬件 | 按真实状态收音、转写、提示及执行；不能靠手工返回助手补步骤 |
| 密码、支付等敏感页面 | 不采集、不自动执行相关动作 |

**第五关：** APK 安装到实际测试手机，按 A 直接指令、A 看物问答、B 确认帮助依次从头跑一遍；保留接口版本、配置和失败日志。保留旧 APK，使用相同签名覆盖安装，避免先卸载导致联系人和设置丢失。

最后交付以真实验收记录为准：哪条链路通过、用的哪台手机、哪里还需手动操作写清楚。若时间不够，优先保住已经验证的 A 两条链路和可停止的 B 单步路径；未通过的环节明确标注，不临时扩大“通用控制所有 App”的承诺。

B 的快速评估至少覆盖 3 段困难操作和 3 段正常操作，记录帮到了几次、不必要地打扰了几次、单步是否正确停止、老人最后是否完成目标。小样本只用来发现问题，不宣称统计准确率；无需为 Demo 先复现论文基准。
