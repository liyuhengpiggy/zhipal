# A / B 新路线接口对齐草案

日期：2026-10-23。本文全部为新增方案，需硬件、Android、视觉和云端负责人一起确认并实现。现有 0.6.2 APK 不认识这里的 A/B 确认上下文；仅增加字段不能认为旧 APK 自动支持。

**先按按钮来源分开，再转写和处理。**A/B 有独立的任务目标、提问和状态；不使用一个智能分类器决定录音属于 A 还是 B。A 含糊时不转 B，B 补充目标时不转 A，B 不调用硬件实物拍照接口。

## 1. 先统一五种编号

| 编号 | 用处 |
|---|---|
| `session_id` | 本次手机与设备的连接会话；重连换新值，避免旧结果串入 |
| `task_id` | 一次任务主线，关联提问、照片、云分析、操作和记录 |
| `event_id` | 一段录音或一次事件的唯一编号；同一次重传保持编号 |
| `prompt_id` | 手机提出的一条帮助问题；回答必须绑定这个编号 |
| `frame_id` | 同一任务下的一张图片编号 |

屏幕预测继续复用现有 `request_id` / `capture_id` 标明本次请求和页面快照，不再另造同义字段。数据库事件仍使用既有 `record_id` 去重；一个任务会有多条事件记录，不能只按 `task_id` 去重。

A 新任务与 B 新任务分别创建自己的 `task_id`，不将 A 的任务编号或目标沿用到 B。B 的澄清、回答和单步操作可以关联同一 B 任务；A 开始时取消 B 旧提问与未执行建议，其迟到结果失效。共享存储和网络工具不能改变这层归属。

## 2. 录音仍然是 WAV，额外携带用途标签

音频继续采用 16 kHz、单声道、16 bit 整数 PCM WAV。文件自身不包含“A 按钮 / B 按钮 / 回答哪个问题”，所以开始发送前必须带一条小控制信息，或在现有录音开始消息中携带标签。音频格式与标签是两件事。

最低标签：`session_id`、`event_id`、`source_button`、`purpose`；若任务已建立，加 `task_id`；B 回答必须有 `prompt_id`。

| 按钮与场景 | `source_button` | `purpose` |
|---|---|---|
| A 新指令 | `A` | `command` |
| B 无待确认提问，主动求助 | `B` | `assist_request` |
| B 回答当前帮助提问 | `B` | `assist_reply` |

**不得仅靠“手机这时似乎有弹窗”推断 B 的录音用途。**没有有效 `prompt_id` 的 `assist_reply` 不执行；也不降级成 A 新指令。

Android 接收控制标签时先验证组合：`A + command` 只交 A 模块；`B + assist_request / assist_reply` 只交 B 模块。来源缺失、标签矛盾或版本不支持时明确回报失败，不靠 WAV 内容猜归属。可以使用同一个转文字工具，但输出必须回到原来的模块，不能再汇入统一智能任务分类器。

麦克风、音频传输和手机动作按先后顺序使用，一次只有一段录音、一个待执行动作。A 任务开始后 B 暂停观察、推理与提示；完成后清掉旧事件并冷却，再按原开关恢复 B。已发出的原子动作不能承诺撤回。

### 传输选择

为了保留已在用的裸 WAV，建议新增一个很小的 `recording_meta` 控制消息：手机确认接受标签后，硬件再照旧按顺序发送完整 WAV；一次只能有一段录音。这不是把 WAV 改成 JSON，也不要求把录音塞进这条控制消息。

如果硬件目前已使用 `audio_start / audio_chunk / audio_end`，可以改为在该开始消息里携带相同标签，复用已有分块流程。**首次 30 分钟只冻结一种实际传输方式，四人必须使用同一种；不要两边分别实现两种。**同一录音的所有块需绑定同一编号。

裸 WAV 控制消息草案：

```json
{
  "v": 2,
  "type": "recording_meta",
  "id": "rec-42",
  "data": {
    "session_id": "session-7",
    "event_id": "rec-42",
    "task_id": "task-12",
    "source_button": "B",
    "purpose": "assist_reply",
    "prompt_id": "prompt-9",
    "format": "wav",
    "size": 160044
  }
}
```

`size` 是完整 WAV 文件的实际字节数。手机确认后回 `ack`，`event_id` 对应 `rec-42`、`status` 为 `ready_for_audio`；未确认就不发送音频。新消息、回包状态、标签保存与超时均需新增，0.6.2 尚未实现。可加完整文件 SHA-256 检验传输；若不做，不能声称已检出所有录音损坏。

应在初次连接交换协议版本和能力。旧 APK 不返回新协议 ready 时停止该新任务，不让 B 回答悄悄落入旧的裸 WAV 命令通道。不要只把现有 `v` 改成 2 而不实现接收与版本判断。

同一个 `event_id` 重传只补传或回已有结果，不能再次拨号。断线后未完成文件清理，旧会话的回答、云结果全部失效。新任务是否自动恢复由调度器决定，本次 Demo 默认不补执行旧动作。

## 3. 提问要双向通知硬件

手机显示提问时，把 `task_id`、`prompt_id`、剩余有效期、问题摘要发给硬件；硬件知道下一段 B 录音应绑定哪个提问。提问取消、过期、已完成，也通知硬件清除等待状态。

这里的帮助提问只属于 B。A 的转写失败或重说提示不创建 B 的 `prompt_id`；A 的补充说明仍由 A 接收。B 无待确认问题时按主动求助处理，有问题时严格核对编号，不能将失效回答当成新命令。

录音完成后手机分开回传状态：收齐文件、转写完成、等待补充、已请求执行、已观察到页面变化、取消、失败。`ack` 只表示接收确认，`intent_requested` 只表示已请求系统操作，不表示电话接通或视频已完成。

## 4. 实物视觉任务

该接口只供 A 的实物问答调用。B 需要看手机页面时使用屏幕预测接口，不发硬件拍照命令。

推荐路线：

`手机生成 task_id → BLE 请求硬件拍照 → 硬件 Wi-Fi 上传图片 → 云端分析 → 手机按 task_id 获取结果`

硬件拍照命令含任务编号、最多候选帧数和实际上传位置 / 上传凭证。凭证由服务发放，不把数据库密码或模型密钥写进固件和 APK。

上传信息：`task_id`、`frame_id`、设备标识、拍摄时间、格式和大小。问题文字由手机提交给同一任务；云端必须能将问题与图片按编号关联，不能用“数据库里最新一张”猜配对。

视觉返回建议包含：

- `task_id`、`status`：`processing / succeeded / unreadable / no_evidence / failed`。
- `answer`：供手机朗读的简短答案。
- `evidence_text`：对应包装原文，读不到时为空。
- `message`：失败或无法判断的原因。
- `frame_id`：答案依据的图片，便于查错。

这些字段名是新约定，朋友如果已有不同字段，集中在手机网络适配层映射。不要假定旧 `/analyze` 已返回这些字段。

手机先创建任务，再请求硬件拍照或允许后续挂图。图片先到、问题后到时，服务保留同一任务关联并明确等待状态；不能拿别人的照片代替。

## 5. 屏幕援助预测

该接口属于 B。请求使用现有 `request_id / capture_id`，补充 B 自己的 `task_id`、用户在 B 当前任务中明确表达的目标、近期事件摘要、当前软件和窗口、真实可操作候选。没有 B 目标时留空，由 B 询问；不得读取 A 任务目标来补齐。必要截图只为这一请求使用。

返回按能力分为：

- `offer_help`：有具体、可解释的帮助建议，需要用户确认。
- `clarify`：目标不明，返回一个简短问题。
- `no_op`：无需打扰或无法提出可靠建议。

建议含 `suggestion_id`、`question`、候选引用、模型分值与简短依据。`suggestion_id` 是模型建议编号；`prompt_id` 是手机实际展示的问题编号，手机负责关联二者。

模型不返回供手机盲目执行的自由脚本；候选必须来自手机实际页面。确认后读取新页面，如果旧候选不再适用，则用同一目标重新定位或请求新预测，不复用旧坐标。

不沿用现有“预测返回就立即执行”的路径处理 B；增加等待回答状态。用户纠正目标时更新任务，不把一句“对，不过是儿子”当成旧目标的纯同意。

B 回答含有“打开某软件”“和某人视频”等文字时，仍是 B 的求助目标或回答，不调用 A 的通用指令入口。确认的是哪一步必须明确；若只确认了大目标而下一步仍不明确，先补问或解释，不连续执行。执行一个步骤后检查变化并结束本轮动作。

## 6. 云端服务名称与故障

现有云端由同学负责。建议对齐以下四种能力即可，不规定必须新建四套服务：

| 能力 | 应对齐的接口内容 |
|---|---|
| 服务可达 | 手机能访问的健康检查 URL |
| 实物问答 | 创建 / 上传 / 取结果的实际 URL、方法、字段与状态 |
| 屏幕预测 | 请求上下文、返回建议 / 问题、超时和取消方式 |
| 事件落库 | 实际保存 URL、鉴权、按 record_id 去重和保存确认 |

本地局域网地址需用手机能访问的电脑 IPv4 或部署域名，不使用手机的 `localhost`。电脑、手机与 ESP32 应能互通；Wi-Fi 热点的设备隔离也需检查。

超时、鉴权失败、照片模糊、结果编号不符、任务取消要有明确错误状态。HTTP 200 不等于分析成功；不匹配任务编号的结果不得显示为本次答案。

记录接口独立快速落库。成功返回既有 `{ "ok": true, "record_id": "原编号" }`；模型耗时不塞进同一次事件写入请求。原始媒体有保留期限时，后台同时删除对象存储文件、缓存与对应引用。

B 的近期操作、当前目标和待回答提问放手机短期状态中，不要求先写入或读取数据库。数据库失败只重试保存事件，不重做拨号或页面点击；这不取消产品已有的跨手机同账号历史记录需求。

## 7. 联调前各人交付什么

硬件：实际服务 / 特征 UUID、固件版本、A/B 状态说明、一个带标签的真实 WAV、一次带任务编号的真实拍照上传。

Android：相同字段的收包日志、A/B 分别的转写内容、各自任务与提问编号、跨 App 接收验证、一次执行结果与事件记录；补充 A/B 不串任务、A 处理期间 B 不提示、B 不启动硬件相机的验证。

视觉：一张测试照片与真实回答、一张看不清样例与真实失败格式；照片更换后结果应变化。

云端：手机可访问地址、接口文档、脱敏请求与响应、一个可查的任务、去重验证、媒体清理规则。不通过聊天发送真实密钥。

每一条失败先根据任务编号和阶段日志找责任环节：录音 / BLE / ASR / 分流 / 拍照 / 上传 / 云分析 / 结果查询 / 确认 / 动作 / 落库。不要把所有失败统一写成“分析失败”。
