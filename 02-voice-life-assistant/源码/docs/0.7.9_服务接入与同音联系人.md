# 0.7.9 服务接入与同音联系人联调

本版为 `0.7.9`（versionCode 20，包名 `cn.seniorvoice.demo`），按队友的 [APP_SERVER_HANDOFF 参考原文](APP_SERVER_HANDOFF_参考原文.md) 对齐 `medicine-ocr` 服务。该文件描述的是接口契约，没有提供真实电脑局域网 IP、已部署公网地址或服务器令牌，不能据此认定任何服务已经可用。本轮不把电脑协议测试或模拟响应当成真实手机、硬件和模型调用成功。

## 先从服务同学处拿到两项配置

需要服务根地址和 `VISION_API_TOKEN` 对应的服务器访问令牌。根地址示例为 `http://<电脑局域网IP>:8000`，占位符必须替换成服务电脑当前 IPv4，不能原样填写。手机与 ESP32 均须能访问这个地址；手机中的 `127.0.0.1` 指手机自己。若是异地或正式访问，使用实际部署的 HTTPS 根地址。

手机只保存服务器访问令牌。硅基流动 `VISION_QWEN_API_KEY` 留在服务端环境中，不填入 APK，不发到日志或共享文档。旧 Render 地址、旧 OCR 地址和过去使用的内网 IP 不自动等于本次交付的 `medicine-ocr` 服务。

局域网 HTTP 仅限调试包显式开启 LAN 选项后使用；正式包要求 HTTPS。电脑服务须监听 `0.0.0.0:8000`，防火墙允许相应入站连接。华为手机、电脑和 ESP32 不应处于禁止设备互访的访客网络。

## 在手机里填到哪里

首页“设置”→“A/B 页面帮助配置”→向下找到“交接视觉服务器（APP_SERVER_HANDOFF）”。勾选“优先使用交接视觉服务器”，填写“交接服务根地址”和“交接服务访问令牌（VISION_API_TOKEN）”；调试包使用内网 HTTP 时再勾选“交接服务允许局域网 HTTP（仅调试版）”，点击“保存交接服务器配置”。根地址仅填协议、主机和端口，不附加 `/api/v1`、`/upload` 或 `/v1`。

若 B 也使用这台服务器，勾选“同时将此服务器用于 B Agent 代理（/v1）”后再保存。它会更新上方 B 代理地址为根地址加 `/v1`、令牌和模型名称，并启用 B Agent；取消勾选不会自动关闭之前的 B 配置。真实 B 页面观察仍需开启系统无障碍、勾选“启用 B 页面帮助”，再点“2. 同意截图分析，开始本次页面观察”。保存服务器不等于同意持续截图。

点击“检查交接服务与模型能力（/health）”，查看 OCR、物体识别和 B 代理状态。健康页只检查服务及能力配置，不能证明云端 Qwen 已实际推理成功。启用交接服务后 A 优先使用它；下方“统一视觉任务接口”和独立旧 OCR 配置保留兼容，不必为了新服务重复填写。

## 三条业务使用同一个根地址，但协议不同

| 业务 | 手机调用 | 图片与返回 |
| --- | --- | --- |
| A 读取文字、生产日期、药盒文字 | `POST /api/v1/vision/tasks` → `PUT /api/v1/vision/tasks/{task_id}/frames/{frame_id}` → `GET /api/v1/vision/tasks/{task_id}` | PUT 原始 JPEG，带 Bearer、X-Task-Id、X-Frame-Id；异步返回 answer、evidence_text 和候选提示 |
| A 识别眼前物体、图片问答 | `POST /api/v1/object-recognition` | JSON 的 images 使用 JPEG Base64 data URL 或服务可访问图片 URL；返回 answer、evidence_text 和 review_required |
| B 当前手机页面帮助 | `POST /v1/chat/completions` | OpenAI-compatible messages，截图为 image_url/Base64；返回模型文本，由手机解析为待确认建议 |

这与 0.7.8 文档中提议的“所有视觉模式共用一个任务端点和短期上传凭证”不同。本版对接应以新交接文档为准，不能把 OBJECT 请求继续发到 OCR task 端点，也不能要求新服务必须返回旧契约的 mode、upload_url、expires_at 或推理标记。0.7.8 的协议文档仅保留历史参考。

OCR 的 task_id 仅允许英文字母、数字、下划线和短横线，长度 1～64；新任务使用新编号。服务支持 expected_frames 1～4，上传必须绑定本次 task/frame，不能借用“最后一张照片”。JPEG 单图最大 8 MiB、1600 万像素，PUT 的正文不是 multipart、JSON 或 Base64。问题在录音之后已明确时随创建一起发送，不需调用 PATCH；PATCH 仅适用于先拍照后补问题的流程。

## 手机选图与眼镜拍照的实际区别

本版常规 A 流程使用单张 `f0`。手机选图时，APK 读取真实 JPEG：OCR 由手机 PUT 上传；物体识别由手机转 Base64 调用独立端点；同时询问文字和物体时，使用同一张图依次完成 OCR 和物体识别，再合并两部分结果。服务支持的多帧能力不等于 APK 已提供 1～4 张图片选择界面。

眼镜 OCR 则由 APK 先创建任务，通过 BLE `capture` 通知 ESP32，携带硬件 `task_id`、服务 `vision_task_id`、`frame_id=f0`、PUT URL 和必要上传头；ESP32 通过 Wi-Fi 直接上传 JPEG，手机按服务任务编号查询。此版交接服务的上传鉴权是服务器 Bearer 令牌，不是 0.7.8 提议的短期单任务凭证；固件需识别 capture 的 upload_headers 并仅用于该服务请求，不把令牌输出到公开串口或日志。

眼镜物体或组合识别还需要把本次照片的可读取 URL 回传给手机：`image_ready` 必须携带匹配的硬件 task_id、vision_task_id 和 `f0`，以及 url/image_url。APK 只从已配置的服务源下载当前 JPEG，再转 Base64 调用物体端点；不会把“上传完成”当成已有可分析图片，也不会读取 latest 缓存。新交接文档没有说明图片下载 URL 的生成接口，需由服务与固件同学对齐；缺少这个 URL 时应先完成手机选图通路，不能宣布眼镜物体识别已闭环。

新服务模式的一次流程共用最多约 180 秒预算，覆盖健康检查、创建、上传/等图、轮询及物体请求；取消或新任务会使旧回包失效。单独 OCR 可按已保存的原服务/任务编号恢复查询；不会为恢复查询自动重传照片或重建一个不同任务。组合与物体请求不使用 OCR 恢复入口。

## 最短联调顺序

1. 先安装当前版本，按上面的手机入口保存服务根地址和服务器令牌。内网 HTTP 调试时显式启用 LAN；先不启动 B 页面观察。
2. 点击“检查交接服务与模型能力（/health）”。不需要令牌，但必须核对 `ready=true`、`database=ok`、OCR 模型状态和能力字段。只有 HTTP 200 或 `status=ok`，不能证明 OCR、Qwen 或 B 均已就绪。
3. 在同一配置页点击“服务器通路测试（选图 → 服务器 → 手机结果）”→“选择测试 JPEG”，选择清晰的真实药盒图。把“图片问题”设为“生产日期是什么”，点“单独测试交接 OCR（原始 JPEG → 异步任务）”。检查创建、原始 JPEG 上传、轮询终态、answer 和 evidence_text；字段候选应与原图一致。
4. 换一张普通实物 JPEG，问题改成“这是什么”，点“单独测试交接物体识别（真实图片 → Qwen）”。检查确实走 `/api/v1/object-recognition`，答案来自当前图片。再用“单独测试交接组合（同图 OCR + 物体识别）”检查同一图片的两部分结果；服务错误不能显示为成功。
5. 换成允许上传、没有个人信息的页面截图，点“单独测试 B Agent”。检查截图 Base64 输入、兼容 choices 响应和现有规划格式解析。本项不会操作手机，也不等于真实 B 按钮确认通过。
6. 最后接真实眼镜，验证 A 录音→本地 ASR→本次拍照→指定服务→手机显示及 TTS；再验证 B 停留询问→B 录音→当前建议→再次语音确认→执行一步并停止。A 开始后，旧 B 提议和确认均须失效。

选图测试页会显示各条通路的阶段文字，并在结束后弹出“服务器通路测试结果”。“测试全部已配置通路”在交接服务启用时依次测试交接 OCR、物体、组合，B 代理已配置时再测试 B Agent；不建议先用全部测试代替单条定位。开始测试会取消原 A/B 任务并结束本次 B 页面观察；完成后如需真实 B 测试，要回到设置重新同意开始观察。“取消本次测试”使该次结果失效，不应再弹出旧答案。

OCR 成功应在手机显示服务器 answer、evidence_text 和需要核对的提示；现有朗读由手机系统中文 TTS 完成。服务默认返回结构化文字，不是下发眼镜播放的语音文件。`review_required=true` 的日期、药名、剂量等需要结合原图核对，不能把候选结果包装成确定结论。

普通 A 识别和选图通路测试是两个入口：要验证 A 结果页与手机朗读，在配置页“照片问题”中输入问题，点击“选择 JPEG 测试识别（作为新 A 任务）”；该入口按问题选择 OCR、物体或组合。朗读需勾选页面顶部“朗读 A 结果和 B 确认问题（手机中文 TTS）”，可先点“测试手机中文朗读”。服务器通路测试页的结果弹窗本身不作为 TTS 验收证据。

B 继续复用已有 MobileAgentB：规划返回 `### Thought ###` / `### Plan ###`；点击提议返回 `### Thought ###` / `### Action ###` / `### Description ###`，Action 只能选择本次真实控件列表中的 target_id。服务转发模型文本不会自动使所有自由文本变得可执行；模型不能直接控制手机。任意 clarification JSON 不是本版 B 的通用解析协议。

## 同音联系人如何使用

联系人仍保存在本 App 内，不读取系统通讯录，不把号码发送给大模型。首次在首页设置中保存正确姓名和号码；本地 ASR 完成后先匹配整个姓名，再考虑可确定的同音字。

例如已保存“乔乔”，ASR 却写成“瞧瞧”：系统可找到同音候选“乔乔”，先显示并朗读“要拨打吗”。在 30 秒内再次按硬件 A 录音说“确认”才请求拨号，说“取消”则结束；也可以在手机提示中选择。确认属于 A，不会改归 B。若本来识别到的姓名与已保存姓名完全一致，则保留现有直接请求拨号流程，不增加这次同音确认。

若保存了多个同音姓名，提示会列出姓名和号码尾号；按 A 说“第一个”“第二个”等选择明确的一项，或在手机提示中选择。只有一个候选时“确认”才可直接选中；多个候选时单说“确认”不会猜选。超过 30 秒、取消、没有听清、联系人已修改或任务已变化时不拨号，重新说完整指令即可。候选过多时要求使用完整姓名。

不同联系人即使号码相同，也不凭共享号码认定为同一个人；仍须明确选择。号码格式允许去掉空格、括号、横线及全角形式，但 `+86` 与不带区号的号码不自动合并。同一联系人有多个不同号码时也不能自行挑选。本 App 当前设置页每个保存称呼对应一个号码。

匹配使用完整逐字音节序列，忽略普通话声调，但保留 `lü/lv` 与 `lu` 的区别；“西安”的 `xi/an` 不会等于“先”的 `xian`。不采用姓名子串、拼音首字母、任意近音或编辑距离猜选，英文和数字按字面处理。只为有限的常见姓名/亲属称呼字提供保守同音替换；多音字和未支持字符保留原字，不能承诺任意中文姓名都可同音匹配。

同音转换使用 Android API 29 及以上的系统 ICU，系统能力异常时回退为精确姓名匹配；Android 8/9 保持精确匹配。HarmonyOS 版本号不直接等于 Android API 级别，目标 Mate30 仍需真机查询并验证。电话权限、手机解锁和系统拨号条件仍须满足；其他 App 前台时的提示/启动依赖已开启的助手无障碍服务。

同音拨号建议先用可接听的测试号码验证。该操作会实际请求发起通话，不是通讯录搜索演示。

| 测试 | 预期 |
| --- | --- |
| 保存“乔乔”，说“给乔乔打电话” | 完整姓名精确命中，沿用现有拨号流程 |
| 仅保存“乔乔”，将 ASR 文本识别为“给瞧瞧打电话” | 提供“乔乔”候选；确认前不拨号，再按 A 确认后仅请求一次 |
| 同音候选提示后按 A 说“取消” | 清除候选，不拨号 |
| 保存多个不同号码的同音姓名 | 列出候选，需明确选择，不按第一个自动拨号 |
| 候选提示后等待超过 30 秒再说“确认” | 旧确认过期，不拨号 |
| 使用不支持的多音字、子串、拼音缩写或吕/鲁互换 | 无可靠唯一匹配就停止，要求使用保存的完整姓名 |

## 服务错误应怎样定位

| 现象 | 处理 |
| --- | --- |
| 手机完全访问不到 `/health` | 查服务监听地址、当前电脑 IPv4、端口、防火墙、同网互访和手机 LAN 开关；不要先改模型 |
| ready=false / HTTP 503 degraded | 服务初始化或组件未就绪；等待服务同学处理，避免反复新建任务 |
| 401 unauthorized | 核对根地址和服务器令牌；不要拿提供商模型 Key 代替，也不要循环重试 |
| 409 task/frame conflict | 本次参数与原编号冲突；创建新任务，避免覆盖已绑定照片 |
| 413 / 415 / 422 | 分别检查图片大小、真实 JPEG 与 Content-Type、请求字段和编号格式 |
| 429 queue_full | 等待后重试，限制并发，不同时重传同一个 frame |
| 503 model_unavailable | 查云端 Key、余额、模型权限和网络；手机显示服务不可用，不能伪造成功答案 |
| 长时间 queued/running | 查询原 task_id 并核对服务 worker；到达超时后必须失败结束，旧结果不能覆盖新任务 |
