# WSS 持续收帧接入说明

## 地址与协议

连接 `wss://ai-glasses-backend-7bj3.onrender.com/ws/camera/upload`。
连接建立后，每张图片发送一个完整的 WebSocket **二进制消息**，不要等待逐帧回复；服务端不发送逐帧 ACK。WebSocket 分片由协议栈重组，不要把自定义头与 JPEG 分成两个消息。

| 字节 | 格式 | 内容 |
| --- | --- | --- |
| 0–3 | uint32，小端 | `0x4B564630` |
| 4–7 | uint32，小端 | 板端递增帧序号 seq |
| 8 起 | 原始字节 | 完整 JPEG，包括文件头和文件尾 |

注意：需求中的数值和 ASCII 注释不一致。**实现以数值为准**：`0x4B564630` 小端字节为 `30 46 56 4B`（`0FVK`），而字符串 `KVF0` 对应小端整数 `0x3046564B`。板端应使用约定数值写小端 uint32，不要直接写字符串 `KVF0`。

JPEG 不缩放、不重新压缩后再入接收缓存。板端保持原来的 1920×1080 与相机 quality 10 设置。单张 JPEG 上限 10 MiB，与旧上传接口一致。

## 内存与增强

- 收帧流程只校验头部、大小、JPEG 首尾标记和序号，替换内存最新帧，不写磁盘、不调用 AI、不等待 OpenCV。
- 同一个连接内，`seq <=` 该连接已接收的最大序号时丢弃；新连接首张有效帧可以从 0 或 1 开始。
- HTTP 与 WS 使用不同的序号用途：内部版本号维持 ETag 和增强流程兼容；板端 seq 用于 WS 乱序判断，不受旧 HTTP 上传次数影响。
- 后台增强仍使用原有 CLAHE、亮度稳定和 JPEG 编码参数。只选择最新帧；已经开始的 OpenCV 调用无法强行中止，但结束时若有更新帧，立即丢弃其结果，不发布旧增强图。
- 若持续收帧速度始终高于增强速度，严格丢弃过期结果会使增强网页暂时保留上次完成图；`/camera/latest` 始终可读取最新原图。这是严格过期丢弃的行为，不能将原图收帧 FPS 当作增强显示 FPS。
- 应用没有帧 FIFO。Uvicorn WebSocket 接收缓冲也限制为 1；TCP/TLS/网络层仍可能存在缓冲，板端同样应覆盖待发送旧帧，避免自己积压。

## 原接口与性能字段

保留 `/upload`、`/camera/frame`、`/camera/latest`、`/camera/performance`，旧 multipart 字段仍为 `file`。`/upload` 保留原有临时落盘行为；新 WSS 通道不落盘。

`GET /camera/latest` 返回最新接收原图，字节与板端 JPEG 一致；ETag 与 `X-Frame-Sequence` 继续使用内部版本号，避免 HTTP/WS 混用时缓存冲突。

性能字段新增：

| 字段 | 含义 |
| --- | --- |
| `ws_connected` | 当前是否存在 WS 上传连接 |
| `ws_connections` | 当前 WS 上传连接数 |
| `ws_frame_fps` | 最近 5 秒有效协议帧数 / 5，含被序号规则丢弃的帧；刚开始推流时需等窗口填满再观察稳定速率 |
| `ws_received_total` | 有效协议帧累计接收数，含过期帧 |
| `ws_dropped_out_of_order` | 重复或乱序累计丢弃数 |
| `ws_dropped_superseded` | 被新连接取代后，旧连接迟到帧的累计丢弃数 |
| `ws_active_session` | 当前画面所属连接的服务端递增会话编号 |
| `latest_received_sequence` | 使用 WS 后为最后接受的板端 seq；尚无 WS 帧时兼容旧内部序号 |
| `latest_internal_sequence` | 内部接收版本号，供 ETag 与增强关联 |
| `dropped_after_processing` | 增强完成时因新帧到达而丢弃的结果数 |

`pending_latest_only` 是“当前是否有尚未发布的最新帧”的瞬时状态，不是功能开关。处理完成后变成 false 属于正常行为。等待槽容量仍为 1。

## 重连与单设备约定

当前服务是单进程、全局一个画面。每次 WebSocket 连接分配一个递增会话编号；新连接的首张有效协议帧接管画面并重新建立序号水位。因此板端重启或重连可从 0/1 开始，也可继续原序号，不需要重启 Render。仅建立空连接或发送非法消息不会中断原上传。接管后，所有较早连接的帧均被丢弃，即使序号较大或新连接已经断开也不能抢回画面；上传端需重连建立新会话。uint32 即将溢出时应主动重连。

这是单设备预览，不是多设备隔离。多个独立上传端会按最新有效连接接管同一个画面，应关闭重复上传任务。Render 服务重启或重新部署会清空内存状态。现有连接上的序号必须递增；若固件不重连就在同一连接内归零，仍会按乱序丢弃。

## 部署与验收

本次运行文件改动为 `app/main.py`、`app/camera_preview.py`、`app/enhancement_runtime.py`、`app/__main__.py`。仓库根目录中若有同名旧副本，不是 `python -m app` 使用的入口。只更新 `app/` 下对应文件，不改 OCR 分支。

Render 保持单 worker，启动命令使用 `python -m app`，以应用新增的 WS 缓冲、消息大小及禁用无效 JPEG 压缩设置启动。已有 `uvicorn[standard]` 包含 WebSocket 运行依赖。

验收脚本使用内存生成的 1920×1080 JPEG 测试图，不读取真实相机图片，不调用模型：

```powershell
.\.venv\Scripts\python.exe scripts/smoke_camera_ws.py
```

首次部署、尚无其他 WS 帧时默认发送 `1,2,3,2`。后续重跑自动从已有 WS 水位继续；仅在水位尚未使用时可显式指定 `--start-seq 1`。验收时暂停其他上传客户端，避免它们覆盖同一全局画面。

脚本检查 WSS 连接、最后 seq、过期帧计数、推流频率、最新 JPEG 字节完全一致及 1920×1080 尺寸。协议错误关闭码：文本 1003、格式错误 1008、图片过大 1009。旧的 `smoke_camera_ws_stale.py` 并行验收方式已禁用：新连接现在会接管画面，不能再向实时服务发送合成低序号图作为无干扰测试。

WSS 消除了应用层逐帧等待 HTTP 响应，但实际 FPS 仍取决于板端发送实现、跨洋带宽、TCP 丢包和 Render CPU。需要板端切换新通道后再测真实提升幅度。
