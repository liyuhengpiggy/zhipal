# Wi-Fi JPEG 实时增强：使用与验证

默认使用 **C：EMA 亮度稳定 + 适度 CLAHE，锐化关闭**。算法不需要训练、模型或外部数据集。本轮没有下载数据，没有调用云端视觉模型；测试图在内存中生成。只修改接收端，ESP32-S3 固件和 JPEG 上传协议保持原样。

## 接入现有接收流程

原接口接收并发布最新 JPEG → 独立后台任务读取最新帧 → 一次 OpenCV 解码 → 在 YCrCb 的 Y 通道依次执行亮度稳定、CLAHE、可选锐化 → 一次 JPEG 编码 → 浏览器绘制。

接收接口不等待图像增强。后台只有一个串行 `asyncio.to_thread` 任务，EMA 状态只由该任务访问；只保留最新输入、当前在途帧和最近完成的一对原图/增强图。处理期间的新输入覆盖旧输入，跳过数可查询，不使用无界队列。配置切换会丢弃旧配置的在途结果及计时，重置 EMA 和采样窗口。

默认页面只传输并绘制增强图，勾选“原图对比”才请求同帧原图。上一轮完成后约 15 ms 再检查，不重叠轮询；图像资源及时释放，Canvas 仅在尺寸变化时重设。`GET /camera/latest` 继续返回原图，原模型接口仍接收原图，不会因显示增强自动调用 AI。

## 算法与取舍

亮度均值在 64×48 缩略 Y 通道计算：`s[t] = α*m[t] + (1-α)*s[t-1]`，增益 `g = clamp(s[t]/max(m[t], 1), 0.8, 1.25)`。默认 α=0.15，在 9.5 FPS 时平滑时间常数约 0.65 秒；不混合视频帧，不产生拖影或增加帧缓存。

增亮使用 256 项 LUT，在中间调保持线性增益，在高光加入单调有理肩部，固定黑白端点，避免少量白色灯点阻止其余画面补偿。具体地，K=220、t=K/g、u=max(x−t,0)/(255−t)、p=g(255−t)/(255−K)；x≤t 时输出 gx，否则输出 `K+(255−K)*p*u/(1+(p−1)*u)`。仅当 g>1 时使用肩部；没有 Python 逐像素循环。

分辨率变化、停顿超过 2 秒、相邻原始帧平均亮度跳变超过 45 时重置。相邻缩略图的标准差都不低于 8 时，曝光归一化结构相关性低于 0.75 也重置，减少移动/切镜后的错误补偿。比较的是相邻输入而非 EMA，避免渐变光照触发周期性重置。低纹理画面中的真实光照与镜头移动无法仅凭均值严格区分，这些规则属于保守启发式。

CLAHE 在亮度稳定后执行，clipLimit=2.0、8×8 网格，结果与原 Y 按 50% 混合，限制 JPEG 噪声和局部对比突变。锐化最后执行，Gaussian σ=1.0、strength=0.4，差值小于 3 不增强，差值限幅 ±16；使用 OpenCV uint8 差分、LUT 和原地运算，避免原先多个全帧 int16/float 临时数组。默认关闭锐化，为浏览器和网络保留性能余量，也减少文字光晕。

所有增强共用一个亮度通道，只做一次往返颜色转换。OpenCV 内部线程设为 1，减少线程竞争。不增加 AI 超分、插帧、GPU 或大型模型依赖，也不额外降噪以免损伤小笔画。

## 配置与启动

已有虚拟环境可直接启动，使用单个 Uvicorn worker：

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --no-access-log
```

本机打开 `http://127.0.0.1:8000/`，同网设备使用当前地址 `http://192.168.20.42:8000/`，刷新旧页面加载新脚本。硬件继续使用 `POST http://192.168.20.42:8000/upload`、`multipart/form-data`、图片字段 `file`。服务监听 `0.0.0.0`，页面使用相对接口地址，无需因电脑 IPv4 变化修改接收端代码。该接口仍按现有设置临时保存原图；本次增强和默认基准不额外导出图片。

| 参数 | 默认值 | 可调范围/含义 |
| --- | --- | --- |
| enable_brightness_stabilization | true | 独立开关亮度稳定 |
| enable_clahe | true | 独立开关局部对比增强 |
| enable_sharpen | false | 独立开关锐化 |
| brightness_alpha | 0.15 | (0, 1]，越小平滑越强、适应越慢 |
| clahe_clip_limit | 2.0 | 0.1–4 |
| tile_grid_size | 8 | 2–16，两个方向相同 |
| sharpen_strength | 0.4 | 0–1 |

首页支持 A 全关、B 亮度稳定、C 亮度稳定+CLAHE、D 全开。切换模式保留细调参数，并同步服务器当前配置。单项开关和参数可在 `/docs` 的 `PUT /camera/enhancement` 调整，例如：

```json
{
  "enable_brightness_stabilization": true,
  "enable_clahe": true,
  "enable_sharpen": false,
  "brightness_alpha": 0.15,
  "clahe_clip_limit": 2.0,
  "tile_grid_size": 8,
  "sharpen_strength": 0.4
}
```

PUT 是完整配置替换，省略字段取默认值；配置只在当前进程有效，重启恢复 C。原图支持 JPEG/PNG，接口限制仍为 10 MiB；增强解码限制 1200 万像素、最短边 8 像素。开启增强后输出 JPEG quality=90；全关时返回原字节、不重编码，但仍解码做计时和验证。增强异常回退原图并计入失败数，损坏原图仍可能无法显示。

## 本轮验证结果（2026-10-23）

本轮没有 ESP32-S3 实时输入或真实浏览器显示测量。用户此前观察约 9.5 FPS，不能据此声称已在真实设备上验证优化后 FPS。以下数字是本机实际运行的合成测试，未训练任何模型，不代表实拍文字识别率。

合成输入固定为 1600×1200、JPEG quality=60，包含渐变、σ=2 噪声、多字号文字、细线和白区。四模式使用相同 JPEG；时域变化另外由自动化测试验证。A 是当前链路关闭全部增强的计算基线，仍含新增的后端 JPEG 解码，不等同于原先仅由浏览器解码的架构基线。

离线每模式预热 10 帧、测量 120 帧，顺序执行：

| 模式 | 离线计算吞吐 FPS | 平均解码 ms | 平均增强 ms | 平均编码 ms |
| --- | ---: | ---: | ---: | ---: |
| A 全关 | 201.42 | 4.749 | 0.014 | 0.003 |
| B EMA | 67.27 | 4.741 | 6.534 | 3.154 |
| C EMA+CLAHE（默认） | 44.60 | 4.798 | 13.798 | 3.375 |
| D 全开 | 36.19 | 4.957 | 18.699 | 3.519 |

另通过实际 ASGI 接口、应用生命周期及后台 worker，以 9.5 FPS 定时回放，每模式 95 帧、约 10 秒；没有网络套接字和浏览器，不是 Wi-Fi 接收/屏幕 FPS：

| 模式 | 接口接收 FPS | 处理 FPS | 完成/发送 | 跳过/失败 | 解码 ms | 增强 ms | 编码 ms | worker ms | 接收至就绪 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| A | 9.495 | 9.495 | 95/95 | 0/0 | 6.01 | 0.02 | 0.00 | 6.78 | 16.20 |
| B | 9.497 | 9.497 | 95/95 | 0/0 | 6.05 | 7.60 | 3.68 | 18.29 | 29.16 |
| C（默认） | 9.496 | 9.496 | 95/95 | 0/0 | 6.41 | 16.09 | 3.55 | 26.97 | 37.65 |
| D | 9.497 | 9.497 | 95/95 | 0/0 | 6.33 | 19.28 | 3.83 | 30.39 | 41.53 |

四模式窗口结束时均无待处理帧。9.5 FPS 的单帧间隔约 105.3 ms；本次默认 C 的后台任务约 27 ms，保留了较大计算余量。增强本身约增加 16 ms；开启后还包含重新编码以及原架构没有的后端解码成本。短时回放不能保证持续运行、其他机器、多客户端或浏览器端始终 ≥9 FPS，因此默认采用 C，负载升高可先切 B 或 A。

完整测试 **68 passed**，仅有原有 Starlette TestClient 弃用警告。覆盖原上传功能、损坏图回退、独立开关与参数边界、慢处理只取最新帧、同帧配对、在途配置变更、JPEG/PNG 分别计数，以及亮度闪烁/高光/结构切镜/渐变曝光/文字与噪声。另已通过页面脚本语法检查及 DOM/fetch 模拟验证；这不等于真实浏览器帧率测量。

在确定性 90/100 亮度交替场景，稳态标准差由 5 降到 0.5，均值由 95 到 94.5，说明算法可抑制该合成闪烁。真实运动、自动曝光、失焦、JPEG 噪声和文字可读性仍需真实拍摄验证；增强无法恢复采集时已丢失的细节。

## 观察运行状态与复现

`GET /camera/performance` 返回实际 JPEG 发布接收速率、全部图片接收速率、处理速率、解码/增强/编码/worker 平均耗时、跳过旧帧及失败累计数、处理中与仅最新帧等待状态。速率采用最近 5 秒窗口，启动头 5 秒偏低；耗时最多取最近 120 帧。`processed` 包含异常回退原图。`queue_capacity=1` 表示只保留一个最新待处理输入，另有当前在途任务。

首页单独显示完成 Canvas 绘制的 FPS。`mean_receive_to_ready_ms` 从后端发布输入帧计到增强结果可用，worker 计时包含线程调度、解码、增强、编码；二者都不包含拍摄、Wi-Fi 上传、浏览器解码/绘制，不是端到端延迟。日志约每 5 秒汇总一次。五秒处理速率计数上限为 120 帧，适用于本次约 9.5 FPS；超过 24 FPS 时会低报。

```powershell
# 内存合成测试：默认只向终端输出，不导出图片或结果文件
.\.venv\Scripts\python.exe -B scripts/benchmark_enhancement.py --synthetic --frames 120
.\.venv\Scripts\python.exe -B scripts/replay_enhancement.py --in-process
# 真实输入恢复后，顺序测量四种模式，结束恢复原配置
.\.venv\Scripts\python.exe -B scripts/measure_live_enhancement.py
# 性能统计
curl.exe http://127.0.0.1:8000/camera/performance
```

离线和回放脚本支持 `--input` 读取已有 JPEG。回放 HTTP 模式默认端口 8001，应连接独立测试服务，避免混入硬件流；实时测量脚本默认连接 8000。需要保留结果时显式传 `--output`；离线图片导出还需 `--export-images`。`POST /image/enhance`（字段 `image`）可做单图测试，但每次状态独立，不能测跨帧 EMA。
